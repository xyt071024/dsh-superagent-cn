二、阶段 0：准备（0.5 天）

做什么

#任务产出
0.1核对 DSH 版本范围版本确认表
0.2备份现有 profile 与数据备份文件
0.3准备测试仓库（GitHub 上一个空仓库）测试环境
0.4确认 Node / pnpm / Git 版本环境报告

通过标准

  • DSH 版本落在 0.2.1-rc.1 ~ 0.2.2-rc.1
  • 备份可恢复（试恢复一次）
  • 测试仓库能 git clone

出问题怎么办

问题处理
DSH 版本不在范围升级或降级到 0.2.2-rc.1
没有测试仓库新建一个私有空仓库，零风险
磁盘空间不足预留 ≥2GB（Node + DSH + 依赖）

三、阶段 1：修复地基（0.5 天）

这一步不做完，后面所有工作都是空中楼阁。

做什么

#任务为什么
1.1修 GitHub 源的 CLI 包装问题现在源在空转，一条数据拉不到
1.2加「隔离进程环境变量」开关防止污染同进程其它插件
1.3修平台兼容（4 处）Windows 上原版跑不起来

1.1 具体问题

现象：源状态 error，日志 15 consecutive failed polls，received: 0。

根因：CLI 包装脚本用的是批处理格式，但插件用直接 spawn 的方式调用它，Windows 上不认。

修法：改用可执行文件包装，或直接注入环境变量。

1.2 具体问题

现象：插件会改 process.env.PATH，把 gh/lark-cli 的包装脚本插到最前。

后果：同进程的其它插件调用 gh 时会用到它的账号。

修法：加配置项，融合模式下不改全局环境，改为局部传参。

1.3 四处平台兼容

#问题修法
a无 env 命令改用 spawn 的环境参数
bstateDir 只认 / 开头放宽为同时接受 X:/
c硬编码 bash 工具按平台选 bash/pwsh（两处）
d重启时端口自我抢占启动前先清理旧进程

通过标准

  • 源状态 ready
  • received 计数 > 0（真的拉到数据）
  • 原有插件功能不受影响（逐项测）

出问题怎么办

问题处理
改完源还是 error看具体错误信息，别只看 runtime: ready
原有插件坏了立刻回滚，检查隔离开关是否生效
端口一直冲突换端口，或写启动脚本先杀旧进程

四、阶段 2：核心框架（5 天）

2.1 设置界面骨架（3 天）

#任务验收
2.1.1八分组导航结构能切换，状态保持
2.1.2基本 / 高级两组字段能存能读
2.1.3模型与算力组模型列表能拉到，选择能保存
2.1.4执行模式组开关生效
2.1.5保存/重置/导入导出配置能往返

技术要点：

  • 设置项变化要热生效，不需要重启
  • 保存失败要有明确提示（不能静默失败）
  • 每个字段有默认值，新装即能用

2.2 模型授权与分档（2 天）

#任务验收
2.2.1模型清单拉取能列出可用模型，按 provider 分组
2.2.2逐模型勾选 + 预算勾选能存，预算能算
2.2.3三档策略（统一/分档/多模型）切换后行为不同
2.2.4思考深度分档四档能存
2.2.5用量统计实时显示已用/剩余

验收关键：配了不同模型，实际调用真的用了不同模型（看日志确认，不能只看界面）。

五、阶段 3：连接源接入（6 天）

顺序原则

先做场景最匹配、依赖最少的。

顺序来源天数理由
3.1QQ邮箱1场景最匹配（异步工作请求）、纯标准协议
3.2企业微信1官方 API 最规范
3.3飞书0.5有 CLI，只差应用凭证
3.4Gmail0.5同邮箱逻辑，加代理
3.5QQ1已有桥接，写适配层
3.6微信2最麻烦，放最后

每个源的通用步骤

#任务验收
a实现配置表单能填、能存、能校验
b实现消息翻译平台事件 → 统一 Trigger
c实现回信通道能发回原渠道
d实现权限判断白名单能生效
e接入健康检查状态能显示
f端到端测试真发一条消息，真收到回复

3.1 QQ邮箱的关键点

项说明
收信IMAP IDLE（服务器推送，不用轮询）
认证授权码，不是登录密码
断线自动重连 + 按 UID 游标补拉
线程归并按邮件主题 + References 头

为什么第一个做：协议标准、不依赖任何客户端、场景和「有人发工作过来」完全匹配。

3.6 微信的关键点

这是最难的，必须五层加固：

层手段
进程守护15 秒探活，崩溃重启（指数退避）
端口仲裁启动前清理僵尸进程
双通道主通道挂 → 窗口控件读取
消息去重按消息 ID
熔断连续失败降级告警

诚实预期：4 星是上限。它依赖客户端行为，改版就得跟。不承诺 5 星。

通过标准

每个源都必须做到：发一条测试消息 → 它收到 → 建工单 → 回复到原渠道。

只看界面显示"已连接"不算通过。

六、阶段 4：多会话协同（4 天）

#任务天数验收
4.1难度预判0.5能区分四档，准确率可接受
4.2子会话创建1能开 N 个，各用不同模型
4.3共享任务板1各会话能看到彼此进度
4.4卡死检测与接管1模拟卡死，能检测并接管
4.5汇总回测0.5能合并结果，能退回修改

关键验收：救援流程

必须跑通这个场景：

1. 开 3 个子会话
2. 手动杀掉其中一个（模拟卡死）
3. 主会话应在 90 秒内检测到
4. 读取卡死会话的日志
5. 决定接管
6. 接管者继续，不重复已完成部分

跑不通就是没做完。

七、阶段 5：自我进化（2 天）

#任务验收
5.1任务后复盘能生成结构化经验条目
5.2经验库检索新任务能加载相关经验（≤5 条）
5.3代码扫描能发现冗余，只提 PR 不直接改
5.4红线保护权限/白名单/熔断逻辑不可被自动修改

关键：自我修改必须走 PR，且不能碰红线代码。

十、风险与应对

风险概率影响应对
版本升级导致插件失效高高冻结验证过的版本；升级前先测
平台兼容性问题中高Windows 优先，其它平台标注「未完整实测」
微信频繁失效高中五层加固 + 明确告知「4 星上限」
多会话成本失控中中难度预判 + 日预算上限 + 单任务上限
上游破甲项目停更中低保留源码，可自行维护
API 变更导致连接源失效中中每个源独立熔断，坏一个不影响其它
