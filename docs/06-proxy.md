## 1. 为什么需要代理

部分服务在特定地区访问不稳定：

| 服务 | 问题 |
|---|---|
| GitHub API | 间歇性超时 |
| raw.githubusercontent.com | 常被重置 |
| Gmail IMAP | 直连超时 |
| 部分 npm / pypi 源 | 慢 |

**不是所有来源都需要代理。** 国内的企微、飞书、QQ、QQ邮箱**直连最快**，走代理反而慢。

---

## 2. 三层架构

```
┌─────────────────────────────────────────────┐
│  L1：用户代理（最高优先）                     │
│  · 用户自己配的                              │
│  · 支持手动填 / 拖拽识别                      │
└─────────────────────────────────────────────┘
                  ↓ 没有则
┌─────────────────────────────────────────────┐
│  L2：系统代理                                │
│  · 读系统设置里的代理                         │
│  · Windows: 注册表 Internet Settings         │
└─────────────────────────────────────────────┘
                  ↓ 没有则
┌─────────────────────────────────────────────┐
│  L3：内置代理                                │
│  · 用户提供的订阅                            │
│  · 或复用本地已有的代理程序                    │
└─────────────────────────────────────────────┘
                  ↓ 都没有
┌─────────────────────────────────────────────┐
│  L4：直连                                    │
└─────────────────────────────────────────────┘
```

**优先级**：用户代理 > 系统代理 > 内置代理 > 直连

## 3. 用户代理：两种配置方式

### 3.1 手动填写

```
HTTP   [ http://127.0.0.1:____ ]
SOCKS5 [ socks5://127.0.0.1:____ ]
```

适合知道自己代理端口的用户。

### 3.2 拖拽识别（傻瓜式）

```
┌────────────────────────────────────────┐
│                                        │
│   把代理软件的可执行文件或文件夹          │
│   拖到这里                              │
│                                        │
│        [ 拖拽区 / 点击选择 ]             │
│                                        │
└────────────────────────────────────────┘
```

**识别流程**：

```
用户拖入文件/文件夹
   ↓
1. 扫描目录结构，识别软件类型
   · 看可执行文件名（已知软件的特征）
   · 看配置文件（config.json / clash.yaml 等）
   · 看进程名
   ↓
2. 找到配置里的代理端口
   · 从配置文件读
   · 或从常见默认端口探测（7890 / 1080 / 7891 等）
   ↓
3. 实测端口是否可用
   · 尝试连接
   · 尝试通过它访问一个测试地址
   ↓
4. 成功了 → 保存配置
   失败了 → 提示「识别到 X，但端口不通，请手动填写」
```

**支持自动识别的类型**（示例，实际按特征匹配）：

| 类型 | 特征 |
|---|---|
| 配置驱动型 | 有 `config.yaml` / `config.json`，内含端口字段 |
| 图形客户端型 | 有 GUI 界面，端口写在设置里 |
| 命令行型 | 有内核可执行文件，参数里带端口 |

### 3.3 自动启动与接管

```
检测到代理未运行
   ↓
☑ 自动启动已识别的代理
   ↓
启动程序（可能需要等待 GUI 起来）
   ↓
⚠ 如果需要交互（登录 / 看广告 / 点确认）
   ↓
☑ 自动完成交互
   ↓
用内置浏览器打开，自动点击必要按钮
   ↓
等待连接建立（探测端口 + 测试请求）
   ↓
成功后开始工作
```

**「自动看广告」的说明**：

有些免费代理启动时要看广告才能连接。自动完成的方式是：

1. 打开它的界面（如果是网页版，用内置浏览器）
2. 等待广告计时结束
3. 自动点击「跳过」或「关闭」
4. 确认已连接

**这需要针对具体软件做适配**，不是通用能力。界面上要写清楚「仅支持已适配的软件」。

## 4. 系统代理

```
读取系统代理设置
   ↓
Windows: HKEY_CURRENT_USER\...\Internet Settings
   · ProxyEnable
   · ProxyServer
   ↓
如果开着 → 使用
如果关着 → 跳过
```

**默认开启检测**，因为大多数用户开了代理软件会自动设系统代理。

## 5. 内置代理

### 5.1 三种节点来源

| 来源 | 说明 | 推荐度 |
|---|---|---|
| **用户提供的订阅** | 填一个订阅链接，自动拉节点 | ★★★★★ |
| **复用本地已有** | 用已识别的代理程序 | ★★★★★ |
| **内置免费节点池** | 内置一批公共节点 | ⚠ 见下 |

### 5.2 关于免费节点 —— 必须说清楚

**公共免费节点绝大多数不干净。**

| 风险 | 说明 |
|---|---|
| **IP 被大量共用** | 一个 IP 可能被上万人用，主流服务会直接拒绝或封号 |
| **凭证可能被截获** | 代理运营方能看你所有流量，包括 token、授权码 |
| **随时失效** | 免费节点的寿命通常以小时计 |
| **速度不稳定** | 可能比直连还慢 |

**本项目的态度**：

- 提供这个选项，但**默认关闭**
- 界面上明确显示风险提示
- **不内置来源不明的节点**
- 建议用户用自己的订阅或复用已有代理

**如果一定要用免费节点，建议**：
- 只用于访问公开内容（不传凭证）
- 关键操作（GitHub 推送、邮箱收信）走用户自己的代理

### 5.3 节点健康检查

```
加入节点池
   ↓
定期测试（每 30 分钟）
   · 能否连通
   · 延迟多少
   · 能否访问目标服务
   ↓
评分
   ↓
调度时优先用高分节点
   ↓
连续失败 3 次 → 暂时移出池子
```

## 6. 分域策略

**不是所有流量都该走代理。**

```
┌─────────────────────────────────────────────┐
│  域名                    走代理？   用哪个    │
├─────────────────────────────────────────────┤
│  api.github.com            ☑      自动       │
│  raw.githubusercontent     ☑      自动       │
│  github.com                ☑      自动       │
│  imap.gmail.com            ☑      自动       │
│  smtp.gmail.com            ☑      自动       │
│  imap.qq.com               ☐      直连       │
│  smtp.qq.com               ☐      直连       │
│  企业微信 API               ☐      直连       │
│  飞书 API                   ☐      直连       │
│  qq.com                    ☐      直连       │
│  bilibili.com              ☐      直连       │
├─────────────────────────────────────────────┤
│  ☑ 未列出的域名默认直连                       │
└─────────────────────────────────────────────┘
```

**为什么国内服务要直连**：走代理反而绕远，延迟更高，还浪费代理流量。

## 7. 失败处理

### 7.1 分级重试

```
请求失败
   ↓
第 1 次重试：立即（换节点）
   ↓ 失败
第 2 次重试：1 秒后（换节点）
   ↓ 失败
第 3 次重试：3 秒后（换节点）
   ↓ 失败
降级：直连试试
   ↓ 失败
报告失败（带上尝试记录）
```

### 7.2 熔断

```
某代理连续失败 5 次
   ↓
标记为不可用（冷却 10 分钟）
   ↓
期间所有请求走其它代理或直连
   ↓
10 分钟后重新测试
```

### 7.3 快速失败

**不要在一个坏掉的代理上等太久。**

```
连接超时：5 秒
读取超时：30 秒
总超时：60 秒
```

## 8. 实现接口

```
proxy.resolve({
  target: 'api.github.com',
  prefer: 'user' | 'system' | 'builtin' | 'direct' | 'auto'
})
→ {
    agent,              // 实际的连接配置
    protocol: 'http' | 'socks5' | 'direct',
    source: 'user' | 'system' | 'builtin' | 'direct',
    node: '节点标识（内置时）'
  }
```

**调用方只需关心「能不能连」，不用关心「怎么连」。**

## 10. 常见问题

### Q：我已经开了代理软件，还需要在这里配吗？

**通常不需要。** 只要代理软件设了系统代理，本项目会自动检测到并使用。

如果它没设系统代理（只开了 TUN 模式），那就直连也能通，也不需要配。

**需要手动配的情况**：代理软件既没设系统代理、也没开 TUN，只监听了本地端口。

### Q：配了代理会不会影响其它程序？

**不会。** 本项目的代理配置只影响自己的请求，不修改系统设置。

### Q：免费节点能用吗？

**不建议用于任何涉及凭证的操作。** 如果你只是偶尔查个公开文档，可以考虑；但 GitHub 推送、邮箱收信这类必须走可信通道。

### Q：为什么国内服务要设成直连？

走代理意味着流量绕到境外再回来，延迟会显著增加。国内的企微、飞书、QQ 直连最快。
