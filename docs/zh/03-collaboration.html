多会话协同机制

这是本项目最核心的扩展能力，也是与官方实现差别最大的部分。

1. 概念：什么叫「异轮会话」

异轮会话 = 主会话在执行任务时，按任务难度动态派生出的子会话。

不是预先定义的，不是固定的。任务简单就不拆，任务难才拆。

2. 为什么需要它

2.1 单会话的局限

问题表现
单点思维一个模型从头想到尾，思路容易固化
串行慢三个独立子任务也要排队做
卡住就完了一处卡住，整个任务停摆
没有交叉验证自己检查自己，容易漏

2.2 多会话如何解决

痛点解法
单点思维不同模型并行，思路互补
串行慢同时开工
卡住就完互相救援（一个卡死，另一个接管）
没有交叉验证互相 review + 主会话最终回测

3. 完整流程（八步）

第 1 步：任务到达

来源可以是任一入口：

  • 邮箱收到工作邮件
  • GitHub 上有人 @ 它
  • QQ / 微信 / 企微 / 飞书 来消息
  • 你直接在对话窗说

第 2 步：难度预判（省流关键）

先跑一次极轻量的评估，用小模型 + 最低思考深度。

输入：任务描述
输出：一个词
   simple   —— 单文件小改动
   medium   —— 多文件协调
   complex  —— 跨模块重构
   extreme  —— 需要架构设计

成本约 50 token，换来后面几百上千 token 的节省。

判断结果直接决定策略：

难度策略
simple主会话自己干完
medium主会话干，必要时开 1-2 个子会话
complex拆 3-4 个子会话
extreme拆 5-6 个子会话 + 多轮迭代

第 3 步：开子会话

主会话决定开 N 个（N = 1~6，由难度决定）
   ↓
每个子会话获得：
   ├─ 独立的 Session（互不干扰的上下文）
   ├─ 独立的工作目录（不会踩到彼此的文件）
   ├─ 指定的模型（可不同）
   ├─ 指定的思考深度（可不同）
   └─ 明确的任务边界（做什么、不做什么）

模型可以完全不同：

子会话模型思考深度为什么选它
Akimi-k2-turbo高擅长长上下文分析
Bclaude-sonnet-4中擅长代码质量
Cdeepseek-v4-pro高擅长逻辑推理

也可以统一模型：如果任务不需要多视角，全用同一个模型更省钱。

第 4 步：建立互联

        ┌──────────────┐
        │   主会话      │
        └──────┬───────┘
       ┌───────┼───────┐
       ↓       ↓       ↓
    ┌─────┐ ┌─────┐ ┌─────┐
    │  A  │←→│  B  │←→│  C  │
    └─────┘ └─────┘ └─────┘
       ↕       ↕       ↕
    ┌─────────────────────┐
    │   共享任务板         │
    │  （谁在干什么、进度）  │
    └─────────────────────┘

三层连接：

连接作用
子 → 主上报进度、请求决策
主 → 子派任务、调整方向、叫停
子 ↔ 子直接通信（不经主会话中转）
全部 ↔ 任务板共享状态，知道彼此进度

第 5 步：协同执行

各自干活
   ↓
每 30 秒写一次心跳 + 进度到任务板
   ↓
定期检查任务板：
   ├─ 我的活干完了？→ 看看谁还没完 → 去帮
   ├─ 别人卡住了？→ 主动询问是否需要帮
   └─ 我的方向可能错了？→ 看看别人的做法

互相帮助的三种形态：

形态例子
补位A 完成自己的部分，去接 B 没做完的
求援B 遇到难题，A 带着上下文来帮忙
纠偏C 发现 A 的方向和 B 冲突，提出来

第 6 步：卡死检测与救援

这是最关键的一环。

每个子会话每 30 秒写心跳
   ↓
主会话定时扫描
   ↓
发现某个超过 90 秒没心跳
   ↓
标记「疑似卡死」
   ↓
读取它的工作日志 + 目录状态
   ↓
判断真实进度
   ↓
三选一决策：
   ├─ 让它继续（只是暂时忙，不是真卡）
   ├─ 重启它（进程挂了）
   └─ 让别的会话接管（真的走不通了）

接管流程：

1. 读取卡死会话的：
   · 工作日志（做到哪一步）
   · 目录变更（改了哪些文件）
   · 最后一条消息（卡在哪）
2. 把这些打包成上下文
3. 交给接管者（通常是进度最快的那个）
4. 接管者继续，不重复已完成的部分

为什么要读日志再接管：不读就直接重做，会重复劳动，甚至覆盖已完成的正确成果。

第 7 步：汇总回测

所有子会话完成
   ↓
主会话收集各自的产出
   ↓
合并（可能有冲突，需要解决）
   ↓
跑完整验证：
   · 编译 / 构建通过？
   · 测试全绿？
   · 功能符合原始需求？
   · 有没有互相矛盾的地方？
   ↓
发现问题？
   ├─ 有 → 退回给对应的子会话修（最多 3 轮）
   └─ 无 → 进入下一步

回测不是走过场。它要独立验证，不能只信子会话的自述。

第 8 步：最终交付

主会话做最后一次完整验证
   ↓
通过 → 输出结果
   ↓
发回原始来源（邮件回复 / GitHub 评论 / IM 消息）
   ↓
记录经验到经验库
   ↓
进入休眠

4. 两种状态下的同一条流程

关键：对话态和静默态的流程完全一致，区别只在界面。

环节对话态静默态
任务到达你说话消息推送
难度预判同样跑同样跑
开子会话窗口可见后台不可见
协同执行你能看到进度只在面板留记录
卡死救援同样做同样做
最终回测同样跑同样跑
交付在窗口显示发回来源

唯一区别：静默态下不弹窗、不打断你。

5. 技术实现

5.1 组件对应

环节用什么实现
开子会话Agent Teams 的 spawn_teammate，或 subagent
不同模型编排层支持 provider / model 覆盖
共享任务板Agent Teams 的 shared task DAG
子会话互发消息send_message（支持冷启动唤醒）
心跳子会话定期写状态文件
卡死检测主会话定时扫描时间戳
进度查询list_agents + 读共享状态

5.3 与官方的差异

维度官方实现本项目
工单之间完全隔离，互不知道互通、共享任务板
卡死处理超时直接杀读日志 → 决定接管/重启
模型每个工单一个模型每个子会话可不同模型
回测执行器自己检查主会话独立最终验证
救援无有（互相补位）

这是对官方的实质扩展，不是配置能实现的。

6. 风险与约束

6.1 已知风险

风险表现缓解
互相等待A 等 B，B 等 A，都不动主会话检测无进展 → 强制指定
重复劳动两个会话做了同一件事任务板先认领再开工
覆盖冲突两个会话改同一文件目录隔离 + 合并时检测
成本失控6 个会话全用强模型分档配置 + 日预算上限
循环救援A 救 B，B 又去救 A救援次数上限（默认 1 次/会话）

6.2 硬约束

约束值说明
最大子会话数6再多协调成本超过收益
心跳间隔30 秒太密浪费，太疏检测迟
卡死判定90 秒无心跳3 个心跳周期
最多退回轮数3回测不过时退回修的次数
单次救援每会话最多 1 次防循环

6.3 什么时候不该拆

不是所有任务都该拆。 以下情况主会话自己干更快：

  • 任务少于 10 分钟
  • 强顺序依赖（第二步必须等第一步完成）
  • 需要频繁共享中间状态
  • 简单问答

难度预判就是为了避免这个。

7. 完整示例

需求：给项目加一个完整的用户登录系统

【T+0】邮件到达：「帮我给项目加个登录系统，支持邮箱密码和第三方 OAuth」
       ↓
【T+3】难度预判 → extreme（涉及数据库、UI、安全、第三方集成）
       ↓
【T+5】主会话拆成 4 个子会话：
        A: 数据库设计与迁移    → claude-sonnet-4（中思考）
        B: 后端 API 与鉴权     → deepseek-v4-pro（高思考）
        C: 前端登录页面        → kimi-k2-turbo（高思考）
        D: OAuth 第三方集成    → gpt-5-mini（中思考）
       ↓
【T+8】建立互联，建任务板
       ↓
【T+10】四个各自开工
       ↓
【T+45】A 完成数据库设计 → 更新任务板 → 去帮 C 写前端表单
【T+60】D 卡在 OAuth 文档不清晰 → 无心跳
【T+62】主会话检测到 → 读 D 的日志 → 发现它卡在解析回调参数
        → 决定让 B 接管（B 已熟悉鉴权逻辑）
【T+63】B 拿到 D 的进度 + 日志，继续做 OAuth
【T+90】全部完成
       ↓
【T+92】主会话合并 → 发现 A 和 B 都改了 user 表结构 → 冲突
        → 退回给 B 修正（以 A 的设计为准）
【T+110】B 修完
       ↓
【T+112】跑完整测试 → 全绿
【T+115】最终回测 → 通过
       ↓
【T+116】回复邮件：「已完成，共 4 个模块，22 个文件，测试覆盖 87%」
       ↓
【T+117】记录经验：OAuth 文档解析易卡 → 下次提前提供示例
