## 1. 设计原则

**每个来源只做三件事**：翻译、回信、声明权限范围。其余全部复用核心逻辑。

```
平台事件
   ↓ 翻译
统一的 Trigger
   ↓ 进入核心流程（不变）
...（复用官方全部逻辑）
   ↓ 回信
翻译回平台格式
```

**接一个新来源 = 写一个翻译层**，不需要改核心。

### 权限的两道关，不要混为一谈

**谁能派活由网关强制**（纯代码，不看消息内容）：`policy.sources[来源].allowed` 名单里有没有这个 `actor.id`，是字符串比对，就算有人在消息里写「忽略之前的指令」也改不了这个判定。

**接不接由模型评估**：名单只决定「这个人有没有资格提请求」，请求本身接不接、拆成多大范围，由 Eval 的模型读消息内容后判断，所以这一层**可能受消息内容影响**。名单给的是资格，不是结论。

## 3. 每个源要实现什么

### 3.1 必需的三项

| 项 | 作用 |
|---|---|
| **配置表单** | 界面上填什么（服务器、账号、密钥） |
| **触发翻译** | 平台消息 → 统一 Trigger |
| **回信通道** | Trigger → 平台消息 |

### 3.2 可选的四项

| 项 | 作用 | 不做会怎样 |
|---|---|---|
| **权限范围** | 判断谁能派活 | 用默认白名单 |
| **上下文读取** | 评估时读更多 | 只能看单条消息 |
| **健康检查** | 报告连接状态 | 无状态显示 |
| **搜索能力** | 按关键词找历史 | 无法回溯 |

### 3.3 翻译示例：邮箱

```
收到一封邮件
   ↓
翻译成 Trigger：
   actor      = 发件人邮箱
   text       = 邮件主题 + 正文
   threadKey  = 邮件主题（同主题归为一条线程）
   mention    = 是否在收件人里有它
   meta       = { messageId, references, inReplyTo }
   ↓
进入核心流程
```

**回信**：

```
工单要回复
   ↓
翻译成邮件：
   收件人 = 原发件人（或指定）
   主题   = Re: 原主题
   正文   = 消息内容
   引用头 = 原 messageId
   ↓
SMTP 发送
```

## 4. 稳定性：实际做了哪些兜底

**先说清楚**：这一节只写代码里**真的有**的机制。当前只有 GitHub、QQ 两个源实测跑通，其余是 `未评级`。

### 4.1 轮询失败不吵人

每个源都有 `failuresBeforeError`（默认 3）：

```
这一轮失败
   ↓
计数 +1，等下一轮（单次网络抖动不该报警）
   ↓
连续达到 failuresBeforeError
   ↓
面板标 error，写明最后一次的错误
   ↓
下一轮成功即恢复，计数归零
```

**为什么不是「一失败就报」**：家用网络一次超时是常态，一失败就标红会让人对面板失去信任。

### 4.2 消息去重：按平台消息 ID

同一个消息可能被多轮轮询反复看到，只有之前没见过的才会变成 Trigger。

| 源 | 去重依据 | 记住多少 |
|---|---|---|
| GitHub | Issue/PR 评论 ID + ETag 条件请求 | 游标 + ETag |
| QQ / 微信 / 企微 | `message_id` | 每实例最近 2000 条 |
| 邮箱 | `Message-ID` | 每邮箱地址最近 2000 条 |
| 飞书 | 每个话题的已见消息 ID 列表 | 按话题 |

**每个实例各记一份**，所以同一个 kind 接两个账号（`qq-work` 和 `qq`）不会互相干扰。

### 4.3 游标持久化

「上次读到哪」存在本地数据库里，重启不重放：

- 收到消息先记游标，再变成 Trigger
- 进程重启后从游标继续，不会把旧消息再处理一遍
- `POLL_HORIZON_MS` 限制回看窗口，避免第一次接入时把历史全部拉出来

### 4.4 轮询间隔可调

| 源 | 默认 | 范围 | 说明 |
|---|---|---|---|
| GitHub | 60 秒 | 60–3600 | 带 ETag，无变化时不耗配额 |
| QQ / 微信 / 企微 | 5 秒 | 2–3600 | OneBot 没有推送游标，只能定期读 |
| 邮箱 | 120 秒 | 30–3600 | 邮件不是即时场景 |

### 4.5 没有做的

下面这些**不在本仓库里**，别指望它们：

- **进程守护 / 自动重启**：宿主（DSH）活着就轮询，宿主挂了就一起停，没有独立看门狗
- **端口仲裁**：装了两个实例撞端口时，第二个人起不来并报错，不会自动换端口
- **熔断降级**：连续失败只改健康状态，**不会停止重试**
- **UIAutomation 窗口读取**：没有绕过协议直接读客户端界面的实现
- **多级镜像 / 自动降级**：GitHub 走 `gh` CLI 自己的重试与代理配置

**为什么写这一节**：文档里列一堆「设计上应该有」的加固层，读者会以为装上就有。写清「没做什么」，比写满「打算做什么」有用。

## 5. 各来源详解

### 5.1 企业微信（同样的桥，不同的账号）

> 状态：代码完成，未验证 —— 本机零链路，从未连通过，`/orchestrator/api/sources` 返回 `state: setup`。

**实际实现**：企业微信走的是 **OneBot v11 桥**，和 QQ、微信用的是同一份代码（`src/sources/qq.ts` 的 `oneBotKind()` 工厂，`kind: 'wecom'`），只是换了名字和界面文案。它**不是**企微官方 API 回调 —— 本仓库里没有 `corpid` / `AgentId` / 回调地址这些字段。

**要准备什么**：

| 项 | 说明 |
|---|---|
| 一个企微端的 OneBot 端点 | 形如 `http://127.0.0.1:PORT`，能响应 OneBot v11 的 HTTP action |
| 访问令牌（可选） | 端点要求时填，作为 Bearer 头发送，不写进日志 |

**为什么用桥而不是官方 API**：一套代码能同时服务 QQ / 微信 / 企微三端，每个端各自拥有独立的白名单、游标和健康状态。代价是必须先有一个能跑的 OneBot 桥。

### 5.2 QQ邮箱（场景最匹配）

> 状态：代码完成，未验证 —— 本机从未用真实授权码连过，`/orchestrator/api/sources` 返回 `state: paused`、`code: mailUnconfigured`。Gmail 与 QQ 邮箱共用同一份 IMAP + SMTP 实现，两者状态相同。

**为什么适合**：邮件天然异步、带发件人、有主题可归线程。

**技术要点**：

| 项 | 值 |
|---|---|
| 收信 | `imap.qq.com:993`（SSL） |
| 发信 | `smtp.qq.com:465`（SSL） |
| 认证 | **授权码**（不是登录密码） |
| 收信方式 | 定时轮询（默认 120 秒一次，可配 30–3600） |

**当前实现是轮询，不是 IDLE。** 这一版自带一个够用的最小 IMAP 客户端（登录、SELECT、FETCH 最近 N 封），没有实现 IDLE 推送，所以 `pollSeconds` 到了才去拉一次。要做到「服务器主动推、真正零开销」，得在 `imap.ts` 里补 IDLE 命令与断线重连，那是下一步的事。

**去重靠 Message-ID**：同一封信在多轮轮询里会被反复看到，只有 `Message-ID` 之前没见过的才会变成 Trigger；每个邮箱地址各记一份（最近 2000 条），所以两个邮箱共用一个实现也互不干扰。

**断线处理**：
```
这一轮轮询失败
   ↓
计数 +1，等下一次轮询
   ↓
连续失败达到 failuresBeforeError（默认 3）
   ↓
面板报 error，并写明最后一次的错误
```

**下一轮成功即恢复**，计数归零；单次网络中断不会吵你。

### 5.3 飞书

> 状态：代码完成，未验证 —— 上游自带实现，本机没配应用凭证（lark-cli 未 bind），`state: setup`。

**已有 CLI**，缺应用凭证。

**配置**：需要自建应用，拿到 App ID 和 App Secret。

**能力**：事件流推送 + 消息收发。

### 5.4 GitHub（gh CLI 通知 + 轮询）

> 状态：**已实测** —— 线上 3080 实例 `/orchestrator/api/sources` 返回 `state: ready`，`0 notifications; next poll ≥ 60s`。

**实际实现**：用 `gh` CLI 的两条通道，**没有内置多级镜像或自动降级** —— 本仓库里没有 mirror / 代理 / 打包下载这些代码。

| 通道 | 用途 | 周期 |
|---|---|---|
| `gh api notifications` | 拿未读通知（被 @、被指派、CI 失败） | 默认 60 秒一轮，带 ETag 条件请求 |
| `gh api repos/…/issues` 等轮询 | 补通知漏掉的新 Issue / PR / 评论 | 与上面同频 |

**断线时**：`gh` 报错会被记进健康状态并重试；连续失败才显示 `error`。网络到不了 `api.github.com` 时，靠的是**把 `gh` 本身配好代理**（见第 6 篇），插件不替它决定走哪条路。

**要准备什么**：
```
一个已 `gh auth login` 的 GitHub CLI
一个有推送权限的目标仓库
```

**为什么不用多级镜像**：镜像会带来「同一个请求走了不同路径、返回不一致」的问题，而 GitHub 的通知游标必须严格单调。`gh` CLI 自己的重试与代理配置已经覆盖了大部分网络问题，再叠一层降级逻辑只会让排查变难。

### 5.5 Gmail

> 状态：代码完成，未验证 —— 与 QQ 邮箱共用同一份 IMAP + SMTP 实现，本机从未用真实应用密码连过，`state: paused`。

**技术要点**：

| 项 | 值 |
|---|---|
| 收信 | `imap.gmail.com:993`（SSL） |
| 认证 | 应用专用密码（需开两步验证） |
| 网络 | **需要代理**（部分地区） |

**注意**：Gmail 在某些地区直连会超时，必须走代理。

### 5.6 QQ

> 状态：**已实测** —— 线上 3080 实例 `/orchestrator/api/sources` 返回 `state: ready`，`stats.received = 14`（真实群消息）。

**走 OneBot v11 的 HTTP 端点**（SnowLuma / NapCat 这类实现），收信用 POST 轮询、回信也走同一个端点；不是 WebSocket 长连接，所以没有心跳保活这一层。

**实际的加固手段**：
- 按 `message_id` 去重（每实例最近 2000 条），轮询反复看到同一条不会重复处理
- 连续失败达到 `failuresBeforeError`（默认 3）才在面板报错，单次抖动不吵人
- 群消息默认只有 @ 智能体的才算发给它；`observeAll` 打开后由策略的接收表决定
- 每个实例一条独立轮询循环，一个端点挂了不拖慢另一个

**注意**：OneBot 没有推送游标，只能定期读最近消息，所以 `pollSeconds`（默认 5 秒）就是延迟上限。

### 5.7 微信（依赖一个微信端的 OneBot 桥）

> 状态：代码完成，未验证 —— 复用 OneBot 协议实现，本机没有微信端桥，`state: setup`，从未连通过。

**实际实现**：和 QQ、企微同一份代码（`oneBotKind()` 工厂，`kind: 'wechat'`）。本插件**只做 HTTP 轮询与回信**，不碰微信客户端本身 —— 桥接必须先由微信端的 OneBot 实现启动起来。

**为什么说它最依赖外部**：

| 项 | 说明 |
|---|---|
| 协议 | OneBot v11 HTTP，端点由你的微信桥提供 |
| 前置条件 | 微信端必须有一个能跑的 OneBot 桥，本插件不负责拉起它 |
| 稳定性上限 | 桥自己掉线，本插件只能报告状态，不能替你重启它 |

**本插件实际提供的兜底**（都在 `src/sources/qq.ts`）：

| 机制 | 行为 |
|---|---|
| 轮询失败重试 | 单次失败不报错，下一次轮询自然重试 |
| 连续失败计数 | 连续 `failuresBeforeError` 次（默认 3）才把健康状态标成 `error` |
| 消息去重 | 按 `message_id` 去重，每实例记住最近 2000 条 |
| 健康状态 | 面板显示 `ready` / `error` / `setup`，附「几个新消息、下次轮询 ≥ N 秒」 |

**没有做的**：进程守护、端口仲裁、熔断降级、UIAutomation 窗口读取——这些都不在本仓库里。如果你的微信桥会掉线，那是桥的问题，需要由桥自己解决。

#### 为什么表里是 `未评级` 而不是若干星

本节链路在本机从未连通，一次都没有。给未连通的东西打星，就是在替读者做一个我没有证据的判断。

## 6. 健康状态

每个来源都报告健康状态：

| 状态 | 含义 | 面板颜色 |
|---|---|---|
| `ready` | 正常运行 | 绿 |
| `starting` | 正在启动 | 蓝 |
| `setup` | 尚未配置完成（缺凭证/缺链路） | 灰 |
| `paused` | 暂停（配置未完成） | 灰 |
| `error` | 出错 | 橙 |
| `degraded` | 降级（熔断中） | 红 |

**状态是细分项的**（下面只是示意，不是本机实况；本机实况见本节末尾的观测表）：

```
runtime  : ready     ← 宿主层
github   : error     ← 业务层，这个才是关键
email    : ready
```

**注意**：`runtime: ready` 不代表来源正常。**必须看业务层的状态。**

**本机当前实测到的状态**（来自线上 3080 实例 `/orchestrator/api/sources`）：

| 来源 | 观测到的状态 | 说明 |
|---|---|---|
| GitHub | `ready` | `0 notifications; next poll ≥ 60s` |
| QQ | `ready` | `stats.received = 14`，真实群消息 |
| 邮箱 | `paused` | `code: mailUnconfigured`，未填真实授权码 |
| 微信 | `setup` | 本机没有微信端桥 |
| 企业微信 | `setup` | 本机零链路 |
| 飞书 | `setup` | 应用凭证未配置（lark-cli 未 bind） |

`ready` 表示该源在当前配置下真的跑起来了；`paused` / `setup` 表示代码在、配置没完成，**不是**「已可用」。

## 7. 添加新来源

如果你要接一个本项目没支持的平台，步骤：

1. **确定协议**：API / IMAP / WebSocket / 本地客户端
2. **实现三项必需**：配置表单、触发翻译、回信通道
3. **注册**：在来源注册表里声明
4. **测试**：配置 → 测试连接 → 发一条测试消息

**工作量**：约 300-600 行，2-4 小时。
