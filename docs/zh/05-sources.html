连接源与稳定性

1. 设计原则

每个来源只做三件事：翻译、回信、判权限。其余全部复用核心逻辑。

平台事件
   ↓ 翻译
统一的 Trigger
   ↓ 进入核心流程（不变）
...（复用官方全部逻辑）
   ↓ 回信
翻译回平台格式

接一个新来源 = 写一个翻译层，不需要改核心。

3. 每个源要实现什么

3.1 必需的三项

项作用
配置表单界面上填什么（服务器、账号、密钥）
触发翻译平台消息 → 统一 Trigger
回信通道Trigger → 平台消息

3.2 可选的四项

项作用不做会怎样
权限范围判断谁能派活用默认白名单
上下文读取评估时读更多只能看单条消息
健康检查报告连接状态无状态显示
搜索能力按关键词找历史无法回溯

3.3 翻译示例：邮箱

收到一封邮件
   ↓
翻译成 Trigger：
   actor      = 发件人邮箱
   text       = 邮件主题 + 正文
   threadKey  = 邮件主题（同主题归为一条线程）
   mention    = 是否在收件人里有它
   meta       = { messageId, references, inReplyTo }
   ↓
进入核心流程

回信：

工单要回复
   ↓
翻译成邮件：
   收件人 = 原发件人（或指定）
   主题   = Re: 原主题
   正文   = 消息内容
   引用头 = 原 messageId
   ↓
SMTP 发送

4. 稳定性：五层加固

目标：所有来源 ≥4 星。 这是设计目标，不代表现状——当前只有 GitHub、QQ 两个源实测跑通，其余四个源的加固层尚未在真实链路上验证过。

4.1 L1 — 进程守护

独立看门狗
   ↓ 每 15 秒
探活：进程还在吗？端口通吗？
   ↓
异常 → 自动重启（指数退避：5s → 10s → 20s → 40s，上限 5 分钟）
   ↓
连续失败 5 次 → 停止重启，告警

为什么要退避：不做退避的话，一个坏掉的依赖会被无限重启，反而拖垮系统。

4.2 L2 — 端口仲裁

启动前检查目标端口
   ↓
被占用？
   ├─ 是自己的僵尸进程 → 强制清理
   ├─ 是别的程序 → 换端口或用备用端口
   └─ 不确定 → 报告冲突，等人决定

4.3 L3 — 双通道

关键设计：每个来源至少有两条独立路径。

来源主通道备通道
GitHubAPI本地 git 缓存
微信本地客户端协议窗口控件读取
邮箱IMAPPOP3
企微回调主动拉取

主通道挂掉，自动切备通道。

4.4 L4 — 消息去重

同一消息可能从多条路到达。用平台消息 ID 去重：

收到消息
   ↓
查 ID 缓存
   ├─ 已处理 → 丢弃
   └─ 新消息 → 处理，记 ID（保留 7 天）

4.5 L5 — 熔断保护

某来源连续失败
   ↓ 达到阈值（默认 5 次）
标记为「降级」
   ↓
行为改变：
   · 不再尝试主动拉取
   · 只记录不处理
   · 面板显示橙色警告
   ↓
人工介入或定时探活成功后恢复

为什么需要：一个坏掉的来源如果一直重试，会占满所有连接，拖垮其它来源。

5. 各来源详解

5.1 企业微信（设计上最稳定）

状态：代码完成，未验证 —— 本机零链路，从未连通过，/orchestrator/api/sources 返回 state: setup。

为什么说它稳：企业级官方 API，协议稳定，有完整文档。这是对协议本身的判断，不是对本机链路的验收结论。

两种接入方式：

方式能力复杂度
群机器人 Webhook只能发，不能收极低
应用消息 API能收能发中

推荐：应用消息 API（能收才能派活）。

配置项：

企业 ID (corpid)
应用 Secret
AgentId
接收回调地址（可选，不配则轮询）

5.2 QQ邮箱（场景最匹配）

状态：代码完成，未验证 —— 本机从未用真实授权码连过，/orchestrator/api/sources 返回 state: paused、code: mailUnconfigured。Gmail 与 QQ 邮箱共用同一份 IMAP + SMTP 实现，两者状态相同。

为什么适合：邮件天然异步、带发件人、有主题可归线程。

技术要点：

项值
收信imap.qq.com:993（SSL）
发信smtp.qq.com:465（SSL）
认证授权码（不是登录密码）
推送IMAP IDLE（服务器主动推）

IMAP IDLE 是关键：不用轮询，服务器有新邮件主动通知，真正零开销。

断线处理：

IDLE 连接断开
   ↓
立即重连（1 秒）
   ↓
重连失败 → 退避重试（5s / 15s / 60s）
   ↓
重连成功 → 用 UID 游标补拉断线期间的消息

5.3 飞书

状态：代码完成，未验证 —— 上游自带实现，本机没配应用凭证（lark-cli 未 bind），state: setup。

已有 CLI，缺应用凭证。

配置：需要自建应用，拿到 App ID 和 App Secret。

能力：事件流推送 + 消息收发。

5.4 GitHub（四级镜像）

状态：已实测 —— 线上 3080 实例 /orchestrator/api/sources 返回 state: ready，0 notifications; next poll ≥ 60s。

这是本项目的关键设计，因为 GitHub 在部分地区访问不稳定。

第 1 级：api.github.com          直连
    ↓ 失败
第 2 级：加速镜像                 第三方代理
    ↓ 失败
第 3 级：本地 git 缓存            已 clone 的内容
    ↓ 失败
第 4 级：打包下载                 下载 zip 解压

每一级失败自动降级，不需要人工干预。

配置项：

☑ 主站
☑ 镜像1（加速代理）
☑ 镜像2（本地缓存）
☑ 镜像3（打包下载）

5.5 Gmail

状态：代码完成，未验证 —— 与 QQ 邮箱共用同一份 IMAP + SMTP 实现，本机从未用真实应用密码连过，state: paused。

技术要点：

项值
收信imap.gmail.com:993（SSL）
认证应用专用密码（需开两步验证）
网络需要代理（部分地区）

注意：Gmail 在某些地区直连会超时，必须走代理。

5.6 QQ

状态：已实测 —— 线上 3080 实例 /orchestrator/api/sources 返回 state: ready，stats.received = 14（真实群消息）。

已有桥接，走 WebSocket。

加固点：

  • 心跳保活（30 秒一次 ping）
  • 断线自动重连
  • 重连后补拉离线消息

5.7 微信（重点加固）

状态：代码完成，未验证 —— 复用 OneBot 协议实现，本机没有微信端桥，state: setup，从未连通过。本节描述的是加固设计，不是实测结果。

这是设计上最脆弱的一环，需要五层加固。

为什么脆弱

问题说明
无官方 API只能通过本地客户端
多进程架构四个子进程，任一挂掉全废
端口争抢两个组件争同一个端口
客户端改版腾讯一更新就得跟

五层加固

层手段解决
L1 进程守护15 秒探活，崩溃重启进程死掉
L2 端口仲裁启动前清理僵尸进程端口争抢
L3 双通道主通道挂 → 窗口控件读取单点依赖
L4 消息去重按消息 ID 去重重复处理
L5 熔断连续失败降级告警拖垮全局

L3 是关键：窗口控件读取

原理：Windows UIAutomation 能直接读取微信窗口里的控件树（消息列表、输入框、发送按钮）。

优点：

  • 不依赖任何第三方注入
  • 不修改微信客户端
  • 不走私有协议

缺点：

  • 微信改版后控件结构可能变，需要适配
  • 读取速度比协议慢

为什么这样能到 4 星：有两条独立路径，一条挂了还有另一条。

为什么到不了 5 星

它本质上依赖腾讯客户端的行为。 腾讯可以随时改版，我们只能跟。

4 星是诚实的上限，说 5 星就是骗人。

6. 健康状态

每个来源都报告健康状态：

状态含义面板颜色
ready正常运行绿
starting正在启动蓝
setup尚未配置完成（缺凭证/缺链路）灰
paused暂停（配置未完成）灰
error出错橙
degraded降级（熔断中）红

状态是细分项的（下面只是示意，不是本机实况；本机实况见本节末尾的观测表）：

runtime  : ready     ← 宿主层
github   : error     ← 业务层，这个才是关键
email    : ready

注意：runtime: ready 不代表来源正常。必须看业务层的状态。

本机当前实测到的状态（来自线上 3080 实例 /orchestrator/api/sources）：

来源观测到的状态说明
GitHubready0 notifications; next poll ≥ 60s
QQreadystats.received = 14，真实群消息
邮箱pausedcode: mailUnconfigured，未填真实授权码
微信setup本机没有微信端桥
企业微信setup本机零链路
飞书setup应用凭证未配置（lark-cli 未 bind）

ready 表示该源在当前配置下真的跑起来了；paused / setup 表示代码在、配置没完成，不是「已可用」。

7. 添加新来源

如果你要接一个本项目没支持的平台，步骤：

  1. 确定协议：API / IMAP / WebSocket / 本地客户端
  2. 实现三项必需：配置表单、触发翻译、回信通道
  3. 注册：在来源注册表里声明
  4. 测试：配置 → 测试连接 → 发一条测试消息

工作量：约 300-600 行，2-4 小时。
