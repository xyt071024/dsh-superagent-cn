◆ Super Agent for DeepSeek Harness
中文 English 日本語

タスクフロー全体

本稿は時系列に沿って、1 通のメッセージが到着してから返信されるまで、各段階で何が起き、どのインターフェースを使うのかを完全に再現します。

1. フェーズ 0：プロセス起動

手順動作場所
1設定ファイルを読む~/.dsh/profiles/<name>/cordis.patch.yml
2データベースを開き、ファイルロックを取る<stateDir>/orchestrator.sqlite
3アカウントを検出（gh api user など）デプロイ時チェック
4worker コマンドのシムディレクトリを書く<stateDir>/worker-bin
5メインセッションを作成専用プリセットを使用
6スケジューリングループを起動2 秒ごと

注意：スケジューリングはポーリング（2 秒ごとにスキャン）であり、イベント駆動ではありません。これは公式実装であり、後続の「サイレント状態」への改修でこの層を置き換えます。

2. フェーズ 1：メッセージ到着（パッシブ経路）

2.1 シーケンス

[1] プラットフォームに新着メッセージ
      ↓ ポーリング（既定 60 秒ごと）
[2] Source が取得
      ↓
[3] Trigger に翻訳
      ↓ 記録：送信者、本文、スレッド識別子、言及の有無
[4] 格納 + 重複排除
      ↓ 同じ Trigger は 1 回だけ保存
[5] 帰属を判定
      ├─ 新規スレッド → スレッドを作成し、評価キューに投入
      └─ 既存スレッド → 購読中のチケットへファンアウト（コンテキストとして。委任はしない）
[6] スケジューリングループが検出
      ↓
[7] 候補カードを組み立て
      ↓
[8] メインセッションへ投入

2.2 主要インターフェース

動作インターフェース
メッセージ取得各プラットフォームの API / CLI
Trigger の保存Engine.receive(trigger)
候補コンテキストの参照orchestrator_eval
追加コンテキストの読み込みorchestrator_eval_read
決定の記録orchestrator_eval_decide
決定のルーティングorchestrator_route

3. フェーズ 2：ゲート（純粋なコード）

Trigger が到着
   ↓
gate(trigger, thread, tickets)     ← 純粋関数、モデルなし
   ↓
手順：
   ① 送信者が許可リストにいるか確認
   ② ボットアカウントか確認
   ③ 受入表の該当セルを確認
   ↓
出力は 3 択：
   explicit   —— 明示的リクエスト
   inferred   —— 推定候補
   not admitted —— 破棄

この段階ではメッセージの内容を見ません。 これが権限防衛線の基盤です。

3.1 受入表

各ソースには受入表があり、行が「受信範囲」、列が 3 つの状況です。

セル選択肢既定
名簿にいるが指名されていない推定 / 無視推定
名簿にいないが指名された明示 / 推定 / 無視無視
名簿にもいないし指名もされていない推定 / 無視無視

例：「名簿にいないが指名された」を「明示」に設定すると、「この範囲で誰でも @ すれば仕事を依頼できる」という意味になります。専用のカスタマーサポートグループに向いています。

4. フェーズ 3：評価（モデル）

4.1 成立が必要な 3 つの事実

事実判断基準
① 議論が本プロジェクトを対象にしている他社製品の話ではなく、仮定の仮定でもありません
② 実装の意図がある具体的な変更を実現したいと明確に述べています
③ 方向性が確定している小範囲の局所修正を直接行え、まだ設計を議論している段階ではありません

3 つすべてが成立したときだけ受注します。 1 つでも欠ければ無視します。

4.2 出力構造

{
  "rule_assessments": [
    { "rule_id": "copy",   "matched": true,  "reason": "文案の変更を明確に要求" },
    { "rule_id": "visual", "matched": false, "reason": "視覚調整には該当しない" }
  ],
  "direction": {
    "implementation_requested": true,
    "target_basis": "existing-standard",
    "requires_design_decision": false,
    "evidence": ["原文の引用"]
  },
  "acknowledgement": "何を行うかを一言で説明"
}

注意：rule_assessments は有効なルールごとに必ず 1 件ずつ返す必要があり、合致の有無は問いません。欠けるとエラーになります。

4.3 コンテキストウィンドウ

評価時に参照できるもの：

内容長さ
トリガーの本文最大 4000 文字
スレッドの直近 5 メッセージ各 400 文字まで
トリガーの前後 5 件ずつ隣接する 2 件は 1200 文字まで
関連チケット最大 8 件、進行中のものを優先
その他のメッセージ50 文字の要約、id 指定で展開可能

5. フェーズ 4：受注

orchestrator_route {kind: "accept", ...}
   ↓
単一トランザクション内で完了：
   ├─ Decision を作成
   ├─ Ticket を作成
   ├─ Mandate を作成（ポリシーバージョン / 範囲 / 強度 / 合致ルールを記録）
   ├─ Assignment を作成（起動待ち）
   ├─ Subscription を作成（関連する全スレッドを購読）
   └─ 確認メッセージの送信をキューに投入
   ↓
実行キューへ

冪等性：同じ Trigger ID で重複して受注しても、チケットは 1 つだけ作成されます。

6. フェーズ 5：実行

6.1 エグゼキュータの起動

[1] prepare コマンドを実行（設定されている場合）—— 制限時間 10 分
[2] ディレクトリ <stateDir>/work/<短縮名> を作成
[3] セッションを起動し、worker-<チケットID> と命名
[4] 最初のメッセージを送信：タイトル + タスク説明 + ソースイベントカード

6.2 エグゼキュータのツールセット

カテゴリツール
ファイルread write edit glob grep read_image
コマンドbash / pwsh job_output job_list job_kill
ネットワークweb_search web_fetch
協調subagent send_message list_agents interrupt_agent
その他skill todo_write

6.3 ワークフロー

1. リポジトリ内の AGENTS.md を読む（プロジェクト固有のルール）
2. 範囲を判断：この作業は自分の委任の範囲内か？
   ├─ 範囲外 → 差し戻し（handback）
   └─ 範囲内 → 続行
3. 着手前に確認：何をするのかを一言で明確にする
4. 作業：コード変更 / テスト実行 / 自己検査
5. 長いコマンドはバックグラウンドへ（フォアグラウンドで 5 秒を超えたら自動移行）
6. 報告

6.4 6 種類のレポート状態

状態意味結果
progress内部の進捗誰にも通知しません
waitingこのラウンドは完了、未解決の問い合わせなしアイドルへ移行し、次のメッセージを待ちます
ready完了かつ自己検査に合格「レビュー待ち」へ移行
blocked不足があり、人手の介入が必須「ブロック」へ移行
failed失敗「失敗」へ移行
dropped対応不要クローズし、メッセージは送りません

6.5 バックグラウンド作業の制限

項目値
1 ラウンドのバックグラウンド作業の最長時間30 分
期限到達時の処理shell タスクを停止し、何を停止したかをレポートに明記
サブエージェント継続を許可
人へ引き継ぐときサブエージェントは即時停止、shell タスクは継続可

7. フェーズ 6：返信

7.1 3 つの経路

経路タイミング制約
確認受注時 / 着手前厳格な上限 100 語
結果ready の報告時チケットが実際に準備完了している必要があります
質問人による判断が必要なとき元の質問を逐語的にコピーすること

7.2 送信先のルール

チケットがどのスレッドから来たか → そこへ返す
   例外：質問が人から出た場合 → 質問者のいるセッションへ返す

7.3 100 語は厳格な制約

これは推奨ではなく、トランスポート層での拒否です。

原文："100 words is a hard ceiling, not a writing target. The transport rejects longer IM messages."

日本語では分かち書きの単位で計算され、Markdown リンクのラベルと URL もカウントされます。

8. フェーズ 7：後続メッセージ

8.1 サブスクリプションの仕組み

チケットは受注時に、関連するすべてのスレッドを購読します。以降：

  • スレッド内のあらゆる新着メッセージ → 自動的にチケットへ到達（コンテキストとして。委任はしません）
  • 再度 @ する必要はありません
  • ボットのメッセージや CI の結果も到達します

8.2 チケット終了後の継続

チケット終了（ready/merged/closed）
   ↓
サブスクリプションは維持
   ↓
誰かが同じスレッドで話し続ける
   ↓
自動的に継続（同じ委任、再評価は不要）
   ↓
委任の条件が変わっていた場合 → 再検証に失敗 → 継続せず、評価からやり直し

シナリオ：GitHub で文案変更の依頼が来た

T+0      誰かが Issue で @ してコメント：「このボタンの文言を Save に変えて」

           ① 本プロジェクトが対象 ✓
           ② 実装の意図あり ✓
           ③ 方向性が確定（具体的に Save へ変更）✓
          copy ルールに合致 → 受注
T+65     チケット + 委任 + アサイン + サブスクリプションを作成（単一トランザクション）
T+66     確認を送信：「了解しました：設定ページの『変更を保存』ボタンを『保存』に変更します」
T+66     エグゼキュータ起動：ディレクトリ作成 → セッション起動 → タスク送信

10. 異常経路

10.1 評価タイムアウト

候補がメインセッションに到達した時点で計測開始（既定 120 秒）
   ↓ タイムアウト
キューに入れてリトライ
   ↓ 2 回連続でタイムアウト
3 回目は「未完了」（unavailable）として記録
   ↓
パネルで人手による対応を促す

10.2 エグゼキュータの停止

状況処理
blocked を報告自動入力を停止し、人を待ちます
failed を報告同上
ハートビートなし（タイムアウト）停止の疑いとして記録し、メインセッションが引き継ぎ / 再起動を決定
プロバイダの一時的な障害自動で 3 回リトライ（5 秒から開始し、倍増して最大 300 秒）

10.3 ソースの失敗

状況処理
単一の読み取り失敗エラーをそのスレッドに記録し、次ラウンドでリトライ
連続 N 回の失敗ソースをエラーとしてマーク
ある項目が 1 日失敗し続けるその項目を破棄し、ポーリングをブロックしない

10.4 返信の失敗

状況処理
送信失敗5 秒後からリトライし、倍増して最大 300 秒
セッションがすでに存在しない「破棄」としてマークし、他の場所へは再送しません
ソースが閉じている待機し、破棄しません
