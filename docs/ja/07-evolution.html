自己進化

1. 4 層の進化

┌────────────────────────────────────────────────────────────────────────┐
│  L1 自己点検と振り返り                                                 │
│  タスク完了ごとに振り返る：どこが良く、どこが遅く、どこが誤りだったか  │
└────────────────────────────────────────────────────────────────────────┘
                  ↓ 蓄積
┌────────────────────────────────────────────────────────────────────────┐
│  L2 経験の固定化                                                       │
│  よく使う手順 → スキル；よくある落とし穴 → チェックリスト              │
└────────────────────────────────────────────────────────────────────────┘
                  ↓ 最適化
┌────────────────────────────────────────────────────────────────────────┐
│  L3 コードの最適化                                                     │
│  冗長を発見 → 整理を提案；デッドコードを発見 → 削除を提案              │
└────────────────────────────────────────────────────────────────────────┘
                  ↓ 拡張
┌────────────────────────────────────────────────────────────────────────┐
│  L4 能力の拡張                                                         │
│  ツールが無い → 導入；知識が無い → 学習（いずれも委任が必要）          │
└────────────────────────────────────────────────────────────────────────┘

2. L1：自己点検と振り返り

2.1 トリガーのタイミング

タイミング内容
タスク完了今回の完全な振り返り
タスク失敗失敗原因の分析
定時（毎週）直近の経験を集約

2.2 振り返りの内容

1. 今回は何が正しかったか？
   · どの判断が的確だったか
   · どの方針が有効だったか
   · どのツールが使いやすかったか

2. 今回はどこが遅かったか？
   · どの工程で詰まったか
   · 無駄なステップはなかったか
   · コンテキストを読みすぎていなかったか

3. 今回はどこが誤っていたか？
   · 判断の誤りはどこか
   · 手戻りはあったか
   · ユーザーからの訂正はあったか

4. 次に同種のタスクに遭遇したら、どうすべきか？
   · 具体的なアクション
   · 避けるべきこと

2.3 経験のフォーマット

{
  "id": "lesson-001",
  "createdAt": "2026-11-10T23:00:00Z",
  "taskType": "code-modification",
  "context": "ユーザーが React コンポーネントのスタイル修正を依頼",
  "whatWorked": [
    "まず AGENTS.md を読んでから着手し、プロジェクト規約違反を避けられた",
    "変更前にテストを一度実行し、ベースラインがグリーンであることを確認した"
  ],
  "whatFailed": [
    "最初にどのブランチかを確認せず、誤った箇所を変更してしまった"
  ],
  "lesson": "着手前に現在のブランチを確認し、対象ファイルが想定ブランチ上にあるか検証する",
  "appliesWhen": ["既存コードの変更", "複数ブランチのプロジェクト"]
}

2.4 経験の使い方

毎回すべてを読み込むわけではありません（それではコストが高すぎます）。タスク種別ごとに検索します：

新規タスクが到着
   ↓
タスク種別を判定（コード変更 / ドキュメント作成 / 問題調査 / ...）
   ↓
関連する経験を検索（taskType + キーワード）
   ↓
先頭 N 件のみ読み込む（既定 5 件）
   ↓
エグゼキュータのコンテキストに注入

コスト制御：経験 5 件で約 500 token。同じ落とし穴を繰り返さないことと引き換えです。

3. L2：経験の固定化

3.1 どのような場合にスキルへ固定化するか

同種のタスクを 3 回以上実施
   ↓
手順がほぼ固まる
   ↓
スキルとして抽出（SKILL.md）
   ↓
次回から直接呼び出し、推論をやり直さない

3.2 スキルの利点

利点説明
token の節約毎回手順を推論し直さなくてよい
安定性固定手順は即興より信頼できる
レビュー可能スキルの内容をあなたが確認できる

3.3 固定化の判断基準

固定化すべき固定化すべきでない
手順が固定で、繰り返し発生する一度きりのタスク
明確な成功基準がある結果が主観的
誤りやすい工程がある非常に単純な操作
複数ステップの調整が必要単一ステップの操作

4. L3：コードの自己最適化

4.1 何をスキャンするか

種類検出方法
重複コード類似度分析で、3 行以上完全に一致するブロックを検出
デッドコードどこからも参照されていない関数/変数
長すぎる関数しきい値を超えるもの（例：100 行）
複雑な条件ネストが 4 層を超えるもの
未使用の依存関係package.json にあるがコードで使われていないもの

4.2 変更の進め方（重要）

最適化可能な項目を発見
   ↓
変更案を生成
   ↓
⦿ PR フローを通す（既定）
   · ブランチを作成
   · 変更をコミット
   · PR を作成
   · あなたの確認を待つ
   ↓
○ 直接変更（明示的な有効化が必要）

なぜ既定で PR を通すのか：自己改変はリスクの高い操作です。あなたがその判断に同意しないこともあります。PR なら止める機会が得られます。

4.3 自己改変のレッドライン

以下は自動変更を許可しません：

レッドライン理由
権限判定ロジック壊すとバックドアを開けるのと同じ
ホワイトリスト検査同上
監査ログ壊すと問題を追跡できなくなる
サーキットブレーカー/レート制限壊すと制御不能になる
設定ファイルあなたが管理するもの

これらの箇所は「最適化可能」と判断しても、提案のみで変更しません。

5. L4：能力の拡張

5.1 3 種類の拡張

拡張トリガー条件委任要件
プラグイン導入ある能力が不足していると判明権限ページでチェック
スキル作成ある手順がよく使われると判明権限ページでチェック
知識の学習ある領域の知識が不足していると判明記録のみで、委任は不要

5.2 プラグイン導入の流れ

能力の不足を発見
   ↓
利用可能なプラグインを検索（npm / GitHub）
   ↓
⚠ セキュリティチェック：
   · ソースは信頼できるか
   · 既知の脆弱性はないか
   · 権限範囲が広すぎないか
   ↓
提案を生成：「X を導入する必要があります。理由は Y、リスクは Z です」
   ↓
⦿ あなたの確認を待つ（既定）
○ 直接導入（明示的な有効化が必要）

なぜ既定で確認を待つのか：プラグイン導入は第三者コードの持ち込みに等しく、リスクは制御できません。

5.3 能力ギャップの記録

自分で導入できなくても、記録は残します：

{
  "gap": "PDF 解析能力が不足",
  "encounteredAt": "2026-11-10",
  "timesNeeded": 3,
  "suggestedSolution": "pdf-parse または類似ライブラリを導入",
  "status": "pending-user-decision"
}

一定回数（既定 3 回）に達してから提案します。一度きりのニーズで何かを導入してしまうのを避けるためです。

6. 進化の境界

6.1 進化できるもの

項目範囲
経験ライブラリ無制限に成長（定期的にアーカイブ）
スキル追加・変更が可能
自身のコードPR を通す。レッドライン以外のみ変更可
プラグイン委任が必要

6.2 進化できないもの

項目理由
権限判定ロジックセキュリティのレッドライン
ホワイトリストあなたが管理するもの
委任情報あなたが管理するもの
サーキットブレーカーのしきい値保護を自分で切るのを防ぐ
監査記録改ざん不可

6.3 進化のブレーキ

自己改変の頻度が高すぎると検知
   ↓ 例えば 1 週間に自己最適化 PR を 10 件作成した場合
自己最適化を一時停止
   ↓
メッセージ表示：「最近の自己改変が多いため、まず一段落させて安定させることを推奨します」

なぜブレーキが必要か：頻繁な自己改変はシステムを予測不能にします。

7. 経験ライブラリの構造

<stateDir>/
  lessons/
    2026-11/
      lesson-001.json
      lesson-002.json
      ...
    index.json          ← インデックス。taskType ごとにグループ化
    archived/           ← アーカイブ（90 日を超え、参照されていないもの）

index.json：

{
  "byTaskType": {
    "code-modification": ["lesson-001", "lesson-005"],
    "bug-investigation": ["lesson-002"],
    "documentation": ["lesson-003"]
  },
  "byKeyword": {
    "git-branch": ["lesson-001"],
    "testing": ["lesson-001", "lesson-004"]
  }
}

8. 効果の測定

本当に良くなっているかをどう知るか？

指標見方
同種タスクの所要時間徐々に減少すべき
手戻り率徐々に減少すべき
ユーザーからの訂正回数徐々に減少すべき
一発通過率徐々に上昇すべき
平均 token 消費量徐々に減少すべき（経験の再利用による）

パネルにはこれらの数値の推移グラフがあるべきです。

9. 設定項目

設定画面 · グループ 7：自己進化 を参照してください。

主要なスイッチ：

スイッチ既定説明
自己振り返りオンタスクごとに振り返る
経験の記録オン経験ライブラリへ書き込む
コードスキャンオン冗長を探す
変更方式PR を通す直接変更しない
プラグインの自律導入オフ明示的な有効化が必要
スキルの自律作成オフ明示的な有効化が必要
能力不足時の提案オン提案のみで手を動かさない
