マルチセッション協調

これは本プロジェクトの最も中核となる拡張機能であり、公式実装との差が最も大きい部分でもあります。

1. 概念：「サブセッション」とは何か

サブセッション = メインセッションがタスクを実行する際に、タスクの難易度に応じて動的に派生させる子セッションのことです。

事前に定義されたものでも、固定されたものでもありません。タスクが簡単なら分割せず、難しいときだけ分割します。

2. なぜ必要なのか

2.1 単一セッションの限界

問題現れ方
単一視点の思考1 つのモデルが最初から最後まで考え続けるため、発想が固まりやすい
直列で遅い独立した 3 つのサブタスクでも順番待ちになる
詰まると終わり1 か所で詰まると、タスク全体が止まる
相互検証がない自分で自分を検査するため、見落としやすい

2.2 マルチセッションによる解決

課題解決策
単一視点の思考異なるモデルが並行し、発想を補い合う
直列で遅い同時に着手する
詰まると終わり相互救済（1 つが止まれば、別が引き継ぐ）
相互検証がない相互レビュー + メインセッションによる最終検証

3. 完全なフロー（8 ステップ）

ステップ 1：タスクの到着

ソースはどの入口でもかまいません：

  • メールで仕事の依頼が届く
  • GitHub で誰かが @ してくる
  • QQ / WeChat / WeCom / Feishu からメッセージが来る
  • あなたが対話ウィンドウで直接話す

ステップ 2：難易度の事前判定（コスト管理の要）

まず極めて軽量な評価を 1 回実行します。小さいモデルと最低の思考深度を使います。

入力：タスクの説明
出力：1 つの単語
   simple   —— 単一ファイルの小さな変更
   medium   —— 複数ファイルの調整
   complex  —— モジュールをまたぐリファクタリング
   extreme  —— アーキテクチャ設計が必要

コストは約 50 token で、その後に数百から数千 token の節約が得られます。

判定結果がそのまま戦略を決めます：

難易度戦略
simpleメインセッションが自分で完結します
mediumメインセッションが実行し、必要なら 1〜2 のサブセッションを起動
complex3〜4 のサブセッションに分割
extreme5〜6 のサブセッションに分割 + 複数ラウンドの反復

ステップ 3：サブセッションの起動

メインセッションが N 個起動を決定（N = 1〜6、難易度で決まる）
   ↓
各サブセッションが受け取るもの：
   ├─ 独立した Session（互いに干渉しないコンテキスト）
   ├─ 独立した作業ディレクトリ（互いのファイルを踏まない）
   ├─ 指定されたモデル（異なってよい）
   ├─ 指定された思考深度（異なってよい）
   └─ 明確なタスク境界（何をし、何をしないか）

モデルはまったく別々でもかまいません：

サブセッションモデル思考深度選定理由
Akimi-k2-turbo高長いコンテキストの分析が得意
Bclaude-sonnet-4中コード品質が得意
Cdeepseek-v4-pro高論理推論が得意

統一してもかまいません：多角的な視点が不要なタスクなら、すべて同じモデルにしたほうが安上がりです。

ステップ 4：相互接続の確立

    ┌───────────────────────┐
    │   メインセッション    │
    └───────────┬───────────┘
       ┌────────┼────────┐
       ↓        ↓        ↓
    ┌─────┐  ┌─────┐  ┌─────┐
    │  A  │←→│  B  │←→│  C  │
    └─────┘  └─────┘  └─────┘
       ↕        ↕        ↕
   ┌─────────────────────────┐
   │   共有タスクボード      │
   │  （誰が何を・進捗）     │
   └─────────────────────────┘

3 層の接続：

接続役割
子 → 主進捗の報告、判断の要求
主 → 子タスクの割り当て、方向の調整、停止指示
子 ↔ 子直接通信（メインセッションを経由しない）
全体 ↔ タスクボード状態を共有し、互いの進捗を把握

ステップ 5：協調実行

それぞれが作業
   ↓
30 秒ごとにハートビート + 進捗をタスクボードへ書き込み
   ↓
定期的にタスクボードを確認：
   ├─ 自分の作業は終わった？→ 誰がまだか確認 → 手伝いに行く
   ├─ 他の誰かが詰まっている？→ 支援が必要か自分から尋ねる
   └─ 自分の方向が違うかも？→ 他の人のやり方を見る

相互支援の 3 つの形：

形例
補位A が自分の担当を終え、B の未完了分を引き継ぐ
求援B が難所に直面し、A がコンテキストを持って支援に入る
矯正C が A の方向と B の方向の衝突に気づき、指摘する

ステップ 6：停止検知と救済

ここが最も重要な部分です。

各サブセッションが 30 秒ごとにハートビートを書き込み
   ↓
メインセッションが定期的にスキャン
   ↓
90 秒を超えてハートビートがないものを発見
   ↓
「停止の疑い」としてマーク
   ↓
その作業ログ + ディレクトリ状態を読む
   ↓
実際の進捗を判断
   ↓
3 択の決定：
   ├─ 続行させる（一時的に多忙なだけで、本当には止まっていない）
   ├─ 再起動する（プロセスが落ちた）
   └─ 別のセッションに引き継がせる（本当に行き詰まった）

引き継ぎの流れ：

1. 停止したセッションから次を読み取る：
   · 作業ログ（どこまで進んだか）
   · ディレクトリの変更（どのファイルを変更したか）
   · 最後のメッセージ（どこで止まったか）
2. これらをコンテキストとしてパッケージ化
3. 引き継ぎ先へ渡す（通常は最も進んでいるもの）
4. 引き継ぎ先が続行し、完了済みの部分は繰り返さない

なぜログを読んでから引き継ぐのか：読まずにやり直すと作業が重複し、完了済みの正しい成果を上書きしてしまうことさえあります。

ステップ 7：集約と最終検証

すべてのサブセッションが完了
   ↓
メインセッションが各々の成果を収集
   ↓
マージ（競合する可能性があり、解決が必要）
   ↓
完全な検証を実行：
   · コンパイル / ビルドは通るか？
   · テストはすべて green か？
   · 機能は元の要件を満たしているか？
   · 互いに矛盾する箇所はないか？
   ↓
問題を発見？
   ├─ あり → 該当するサブセッションへ修正に戻す（最大 3 ラウンド）
   └─ なし → 次のステップへ

最終検証は形だけのものではありません。独立した検証が必要で、サブセッションの自己申告だけを信じてはいけません。

ステップ 8：最終納品

メインセッションが最後の完全検証を実施
   ↓
合格 → 結果を出力
   ↓
元のソースへ返信（メール返信 / GitHub コメント / IM メッセージ）
   ↓
経験を経験ライブラリへ記録
   ↓
休眠に入る

4. 2 つの状態で同じ 1 本のフロー

要点：対話状態とサイレント状態でフローは完全に同一であり、違いは UI だけです。

段階対話状態サイレント状態
タスクの到着あなたが話すメッセージのプッシュ
難易度の事前判定同じように実行同じように実行
サブセッションの起動ウィンドウに表示バックグラウンドで不可視
協調実行進捗が見えるパネルに記録が残るだけ
停止時の救済同じように実施同じように実施
最終検証同じように実行同じように実行
納品ウィンドウに表示ソースへ返信

唯一の違い：サイレント状態ではポップアップも割り込みもしません。

5. 技術的な実装

5.1 コンポーネントの対応

段階実装に使うもの
サブセッションの起動Agent Teams の spawn_teammate、または subagent
異なるモデルオーケストレーション層が provider / model の上書きに対応
共有タスクボードAgent Teams の shared task DAG
サブセッション間のメッセージsend_message（コールドスタートからの起動に対応）
ハートビートサブセッションが定期的に状態ファイルを書き込む
停止検知メインセッションが定期的にタイムスタンプをスキャン
進捗の照会list_agents + 共有状態の読み取り

5.3 公式実装との差異

観点公式実装本プロジェクト
チケット同士完全に分離、互いを知らない相互に通信し、タスクボードを共有
停止時の処理タイムアウトで即 killログを読む → 引き継ぎ / 再起動を決定
モデルチケットごとに 1 モデルサブセッションごとに異なるモデルが可能
検証エグゼキュータが自分で検査メインセッションが独立して最終検証
救済なしあり（相互に補位）

これは公式実装に対する実質的な拡張であり、設定では実現できません。

6. リスクと制約

6.1 既知のリスク

リスク現れ方緩和策
相互待ちA が B を待ち、B が A を待ち、どちらも動かないメインセッションが進捗なしを検知 → 強制的に指定
作業の重複2 つのセッションが同じことをしてしまうタスクボードで先に claim してから着手
上書き競合2 つのセッションが同じファイルを変更ディレクトリ分離 + マージ時の検出
コストの暴走6 つのセッションがすべて強いモデルを使う段階別設定 + 日次予算の上限
救済の循環A が B を救い、B がまた A を救う救済回数の上限（既定で 1 回 / セッション）

6.2 ハード制約

制約値説明
最大サブセッション数6これ以上は調整コストが便益を上回ります
ハートビート間隔30 秒密すぎると無駄、疎すぎると検知が遅れます
停止の判定90 秒ハートビートなしハートビート 3 周期分
最大差し戻し回数3検証に通らない場合に修正へ戻す回数
1 回の救済各セッション最大 1 回循環の防止

6.3 分割すべきでないとき

すべてのタスクを分割すべきではありません。 次の場合はメインセッションが自分でやるほうが速いです：

  • タスクが 10 分未満
  • 強い順序依存がある（第 2 段階が第 1 段階の完了を待たなければならない）
  • 中間状態を頻繁に共有する必要がある
  • 単純な Q&A

難易度の事前判定は、まさにこれを避けるためのものです。

7. 完全な例

要件：プロジェクトに完全なユーザーログインシステムを追加する

【T+0】メール到着：「プロジェクトにログインシステムを追加してください。メール + パスワードとサードパーティ OAuth に対応」
       ↓
【T+3】難易度の事前判定 → extreme（データベース、UI、セキュリティ、サードパーティ連携にまたがる）
       ↓
【T+5】メインセッションが 4 つのサブセッションに分割：
        A: データベース設計とマイグレーション → claude-sonnet-4（中思考）
        B: バックエンド API と認証        → deepseek-v4-pro（高思考）
        C: フロントエンドのログイン画面    → kimi-k2-turbo（高思考）
        D: OAuth サードパーティ連携       → gpt-5-mini（中思考）
       ↓
【T+8】相互接続を確立し、タスクボードを作成
       ↓
【T+10】4 つがそれぞれ着手
       ↓
【T+45】A がデータベース設計を完了 → タスクボードを更新 → C のフロントエンドフォーム作成を手伝う
【T+60】D が OAuth のドキュメントが不明瞭なところで停止 → ハートビートなし
【T+62】メインセッションが検知 → D のログを読む → コールバックパラメータの解析で止まっていると判明
        → B に引き継がせることを決定（B はすでに認証ロジックに習熟）
【T+63】B が D の進捗 + ログを受け取り、OAuth を続行
【T+90】すべて完了
       ↓
【T+92】メインセッションがマージ → A と B がどちらも user テーブルの構造を変更していた → 競合
        → B に修正を差し戻し（A の設計を正とする）
【T+110】B が修正完了
       ↓
【T+112】完全なテストを実行 → すべて green
【T+115】最終検証 → 合格
       ↓
【T+116】メールで返信：「完了しました。全 4 モジュール、22 ファイル、テストカバレッジ 87%」
       ↓
【T+117】経験を記録：OAuth のドキュメント解析で詰まりやすい → 次回は先にサンプルを用意する
