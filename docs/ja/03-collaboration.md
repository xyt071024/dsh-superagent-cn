# 03 · マルチセッション協調の仕組み（サブセッション）

[← 前へ：タスクフロー全体](02-flow.md) | [README に戻る](../README.md) | [次へ：設定 UI →](04-settings.md)

---

これは本プロジェクトの**最も中核となる拡張機能**であり、公式実装との差が最も大きい部分でもあります。

---

## 1. 概念：「サブセッション」とは何か

**サブセッション** = メインセッションがタスクを実行する際に、**タスクの難易度に応じて動的に派生させる子セッション**のことです。

事前に定義されたものでも、固定されたものでもありません。**タスクが簡単なら分割せず、難しいときだけ分割します。**

---

## 2. なぜ必要なのか

### 2.1 単一セッションの限界

| 問題 | 現れ方 |
|---|---|
| **単一視点の思考** | 1 つのモデルが最初から最後まで考え続けるため、発想が固まりやすい |
| **直列で遅い** | 独立した 3 つのサブタスクでも順番待ちになる |
| **詰まると終わり** | 1 か所で詰まると、タスク全体が止まる |
| **相互検証がない** | 自分で自分を検査するため、見落としやすい |

### 2.2 マルチセッションによる解決

| 課題 | 解決策 |
|---|---|
| 単一視点の思考 | **異なるモデルが並行**し、発想を補い合う |
| 直列で遅い | **同時に着手する** |
| 詰まると終わり | **相互救済**（1 つが止まれば、別が引き継ぐ） |
| 相互検証がない | **相互レビュー + メインセッションによる最終検証** |

## 3. 完全なフロー（8 ステップ）

### ステップ 1：タスクの到着

ソースはどの入口でもかまいません：

- メールで仕事の依頼が届く
- GitHub で誰かが @ してくる
- QQ / WeChat / WeCom / Feishu からメッセージが来る
- あなたが対話ウィンドウで直接話す

### ステップ 2：難易度の事前判定（コスト管理の要）

**まず極めて軽量な評価を 1 回実行します**。小さいモデルと最低の思考深度を使います。

```
入力：タスクの説明
出力：1 つの単語
   simple   —— 単一ファイルの小さな変更
   medium   —— 複数ファイルの調整
   complex  —— モジュールをまたぐリファクタリング
   extreme  —— アーキテクチャ設計が必要
```

**コストは約 50 token** で、その後に数百から数千 token の節約が得られます。

**判定結果がそのまま戦略を決めます**：

| 難易度 | 戦略 |
|---|---|
| simple | メインセッションが自分で完結します |
| medium | メインセッションが実行し、必要なら 1〜2 のサブセッションを起動 |
| complex | 3〜4 のサブセッションに分割 |
| extreme | 5〜6 のサブセッションに分割 + 複数ラウンドの反復 |

### ステップ 3：サブセッションの起動

```
メインセッションが N 個起動を決定（N = 1〜6、難易度で決まる）
   ↓
各サブセッションが受け取るもの：
   ├─ 独立した Session（互いに干渉しないコンテキスト）
   ├─ 独立した作業ディレクトリ（互いのファイルを踏まない）
   ├─ 指定されたモデル（異なってよい）
   ├─ 指定された思考深度（異なってよい）
   └─ 明確なタスク境界（何をし、何をしないか）
```

**モデルはまったく別々でもかまいません**：

| サブセッション | モデル | 思考深度 | 選定理由 |
|---|---|---|---|
| A | kimi-k2-turbo | 高 | 長いコンテキストの分析が得意 |
| B | claude-sonnet-4 | 中 | コード品質が得意 |
| C | deepseek-v4-pro | 高 | 論理推論が得意 |

**統一してもかまいません**：多角的な視点が不要なタスクなら、すべて同じモデルにしたほうが安上がりです。

### ステップ 4：相互接続の確立

```
    ┌───────────────────────┐
    │   メインセッション    │
    └───────────┬───────────┘
       ┌────────┼────────┐
       ↓        ↓        ↓
    ┌─────┐  ┌─────┐  ┌─────┐
    │  A  │←→│  B  │←→│  C  │
    └─────┘  └─────┘  └─────┘
       ↕        ↕        ↕
   ┌─────────────────────────┐
   │   共有タスクボード      │
   │  （誰が何を・進捗）     │
   └─────────────────────────┘
```
        ┌──────────────┐
    │   メインセッション    │
        └──────┬───────┘
       ┌───────┼───────┐
|---|---|
    ┌─────┐ ┌─────┐ ┌─────┐
    │  A  │←→│  B  │←→│  C  │
    └─────┘ └─────┘ └─────┘
| 全体 ↔ タスクボード | 状態を共有し、互いの進捗を把握 |
    ┌─────────────────────┐
    │   共有タスクボード   │
    │  （誰が何を・進捗）    │
    └─────────────────────┘
それぞれが作業
   ↓
30 秒ごとにハートビート + 進捗をタスクボードへ書き込み
   ↓
定期的にタスクボードを確認：
   ├─ 自分の作業は終わった？→ 誰がまだか確認 → 手伝いに行く
   ├─ 他の誰かが詰まっている？→ 支援が必要か自分から尋ねる
   └─ 自分の方向が違うかも？→ 他の人のやり方を見る
```

**相互支援の 3 つの形**：

| 形 | 例 |
|---|---|
| **補位** | A が自分の担当を終え、B の未完了分を引き継ぐ |
| **求援** | B が難所に直面し、A がコンテキストを持って支援に入る |
| **矯正** | C が A の方向と B の方向の衝突に気づき、指摘する |

### ステップ 6：停止検知と救済

**ここが最も重要な部分です。**

```
各サブセッションが 30 秒ごとにハートビートを書き込み
   ↓
メインセッションが定期的にスキャン
   ↓
90 秒を超えてハートビートがないものを発見
   ↓
「停止の疑い」としてマーク
   ↓
その作業ログ + ディレクトリ状態を読む
   ↓
実際の進捗を判断
   ↓
3 択の決定：
   ├─ 続行させる（一時的に多忙なだけで、本当には止まっていない）
   ├─ 再起動する（プロセスが落ちた）
   └─ 別のセッションに引き継がせる（本当に行き詰まった）
```

**引き継ぎの流れ**：

```
1. 停止したセッションから次を読み取る：
   · 作業ログ（どこまで進んだか）
   · ディレクトリの変更（どのファイルを変更したか）
   · 最後のメッセージ（どこで止まったか）
2. これらをコンテキストとしてパッケージ化
3. 引き継ぎ先へ渡す（通常は最も進んでいるもの）
4. 引き継ぎ先が続行し、完了済みの部分は繰り返さない
```

**なぜログを読んでから引き継ぐのか**：読まずにやり直すと作業が重複し、完了済みの正しい成果を上書きしてしまうことさえあります。

### ステップ 7：集約と最終検証

```
すべてのサブセッションが完了
   ↓
メインセッションが各々の成果を収集
   ↓
マージ（競合する可能性があり、解決が必要）
   ↓
完全な検証を実行：
   · コンパイル / ビルドは通るか？
   · テストはすべて green か？
   · 機能は元の要件を満たしているか？
   · 互いに矛盾する箇所はないか？
   ↓
問題を発見？
   ├─ あり → 該当するサブセッションへ修正に戻す（最大 3 ラウンド）
   └─ なし → 次のステップへ
```

**最終検証は形だけのものではありません**。**独立した検証**が必要で、サブセッションの自己申告だけを信じてはいけません。

### ステップ 8：最終納品

```
メインセッションが最後の完全検証を実施
   ↓
合格 → 結果を出力
   ↓
元のソースへ返信（メール返信 / GitHub コメント / IM メッセージ）
   ↓
経験を経験ライブラリへ記録
   ↓
休眠に入る
```

## 4. 2 つの状態で同じ 1 本のフロー

**要点**：対話状態とサイレント状態で**フローは完全に同一**であり、違いは UI だけです。

| 段階 | 対話状態 | サイレント状態 |
|---|---|---|
| タスクの到着 | あなたが話す | メッセージのプッシュ |
| 難易度の事前判定 | 同じように実行 | 同じように実行 |
| サブセッションの起動 | ウィンドウに表示 | バックグラウンドで不可視 |
| 協調実行 | 進捗が見える | パネルに記録が残るだけ |
| 停止時の救済 | 同じように実施 | 同じように実施 |
| 最終検証 | 同じように実行 | 同じように実行 |
| 納品 | ウィンドウに表示 | ソースへ返信 |

**唯一の違い**：サイレント状態ではポップアップも割り込みもしません。

## 5. 技術的な実装

### 5.1 コンポーネントの対応

| 段階 | 実装に使うもの |
|---|---|
| サブセッションの起動 | Agent Teams の `spawn_teammate`、または `subagent` |
| 異なるモデル | オーケストレーション層が `provider` / `model` の上書きに対応 |
| 共有タスクボード | Agent Teams の shared task DAG |
| サブセッション間のメッセージ | `send_message`（コールドスタートからの起動に対応） |
| ハートビート | サブセッションが定期的に状態ファイルを書き込む |
| 停止検知 | メインセッションが定期的にタイムスタンプをスキャン |
| 進捗の照会 | `list_agents` + 共有状態の読み取り |

### 5.2 データ構造

**共有タスクボード**：

```json
{
  "ticketId": "T-18",
  "sessions": [
    { "id": "A", "model": "kimi-k2-turbo", "status": "running",  "progress": 60, "heartbeat": 1794284787 },
    { "id": "B", "model": "claude-sonnet-4","status": "waiting",  "progress": 20, "heartbeat": 1794284790 },
    { "id": "C", "model": "deepseek-v4-pro","status": "stuck",    "progress": 0,  "heartbeat": 1794284600 }
  ],
  "tasks": [
    { "name": "要件分析",   "owner": "A", "status": "done",    "progress": 100 },
    { "name": "設計立案",   "owner": "B", "status": "running", "progress": 20  },
    { "name": "コード実装", "owner": "A", "status": "running", "progress": 60  },
    { "name": "テスト実装", "owner": "C", "status": "stuck",   "progress": 0   }
  ]
}
```

### 5.3 公式実装との差異

| 観点 | 公式実装 | 本プロジェクト |
|---|---|---|
| チケット同士 | **完全に分離、互いを知らない** | 相互に通信し、タスクボードを共有 |
| 停止時の処理 | タイムアウトで即 kill | ログを読む → 引き継ぎ / 再起動を決定 |
| モデル | チケットごとに 1 モデル | サブセッションごとに異なるモデルが可能 |
| 検証 | エグゼキュータが自分で検査 | メインセッションが独立して最終検証 |
| 救済 | なし | あり（相互に補位） |

**これは公式実装に対する実質的な拡張であり、設定では実現できません。**

## 6. リスクと制約

### 6.1 既知のリスク

| リスク | 現れ方 | 緩和策 |
|---|---|---|
| **相互待ち** | A が B を待ち、B が A を待ち、どちらも動かない | メインセッションが進捗なしを検知 → 強制的に指定 |
| **作業の重複** | 2 つのセッションが同じことをしてしまう | タスクボードで先に claim してから着手 |
| **上書き競合** | 2 つのセッションが同じファイルを変更 | ディレクトリ分離 + マージ時の検出 |
| **コストの暴走** | 6 つのセッションがすべて強いモデルを使う | 段階別設定 + 日次予算の上限 |
| **救済の循環** | A が B を救い、B がまた A を救う | 救済回数の上限（既定で 1 回 / セッション） |

### 6.2 ハード制約

| 制約 | 値 | 説明 |
|---|---|---|
| 最大サブセッション数 | 6 | これ以上は調整コストが便益を上回ります |
| ハートビート間隔 | 30 秒 | 密すぎると無駄、疎すぎると検知が遅れます |
| 停止の判定 | 90 秒ハートビートなし | ハートビート 3 周期分 |
| 最大差し戻し回数 | 3 | 検証に通らない場合に修正へ戻す回数 |
| 1 回の救済 | 各セッション最大 1 回 | 循環の防止 |

### 6.3 分割すべきでないとき

**すべてのタスクを分割すべきではありません。** 次の場合はメインセッションが自分でやるほうが速いです：

- タスクが 10 分未満
- 強い順序依存がある（第 2 段階が第 1 段階の完了を待たなければならない）
- 中間状態を頻繁に共有する必要がある
- 単純な Q&A

**難易度の事前判定は、まさにこれを避けるためのものです**。

## 7. 完全な例

### 要件：プロジェクトに完全なユーザーログインシステムを追加する

```
【T+0】メール到着：「プロジェクトにログインシステムを追加してください。メール + パスワードとサードパーティ OAuth に対応」
       ↓
【T+3】難易度の事前判定 → extreme（データベース、UI、セキュリティ、サードパーティ連携にまたがる）
       ↓
【T+5】メインセッションが 4 つのサブセッションに分割：
        A: データベース設計とマイグレーション → claude-sonnet-4（中思考）
        B: バックエンド API と認証        → deepseek-v4-pro（高思考）
        C: フロントエンドのログイン画面    → kimi-k2-turbo（高思考）
        D: OAuth サードパーティ連携       → gpt-5-mini（中思考）
       ↓
【T+8】相互接続を確立し、タスクボードを作成
       ↓
【T+10】4 つがそれぞれ着手
       ↓
【T+45】A がデータベース設計を完了 → タスクボードを更新 → C のフロントエンドフォーム作成を手伝う
【T+60】D が OAuth のドキュメントが不明瞭なところで停止 → ハートビートなし
【T+62】メインセッションが検知 → D のログを読む → コールバックパラメータの解析で止まっていると判明
        → B に引き継がせることを決定（B はすでに認証ロジックに習熟）
【T+63】B が D の進捗 + ログを受け取り、OAuth を続行
【T+90】すべて完了
       ↓
【T+92】メインセッションがマージ → A と B がどちらも user テーブルの構造を変更していた → 競合
        → B に修正を差し戻し（A の設計を正とする）
【T+110】B が修正完了
       ↓
【T+112】完全なテストを実行 → すべて green
【T+115】最終検証 → 合格
       ↓
【T+116】メールで返信：「完了しました。全 4 モジュール、22 ファイル、テストカバレッジ 87%」
       ↓
【T+117】経験を記録：OAuth のドキュメント解析で詰まりやすい → 次回は先にサンプルを用意する
```
