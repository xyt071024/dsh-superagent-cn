ソースと安定性

1. 設計原則

各ソースがやることは 3 つだけです。翻訳、返信、権限判定。それ以外はすべてコアのロジックを再利用します。

プラットフォームのイベント
   ↓ 翻訳
統一された Trigger
   ↓ コアフローへ（変更なし）
...（公式のロジックをすべて再利用）
   ↓ 返信
プラットフォームの形式へ翻訳

新しいソースの追加 = 翻訳層を 1 つ書くことであり、コアを変更する必要はありません。

3. 各ソースが実装すべきもの

3.1 必須の 3 項目

項目役割
設定フォーム画面で何を入力するか（サーバー、アカウント、鍵）
トリガー翻訳プラットフォームのメッセージ → 統一 Trigger
返信チャネルTrigger → プラットフォームのメッセージ

3.2 任意の 4 項目

項目役割実装しない場合
権限範囲誰がアサインできるかを判定既定の許可リストを使います
コンテキスト読み取り評価時により多く読む単一メッセージしか見られません
ヘルスチェック接続状態を報告状態表示なし
検索能力キーワードで履歴を探す遡れません

3.3 翻訳の例：メール

メールを 1 通受信
   ↓
Trigger に翻訳：
   actor      = 送信者のメールアドレス
   text       = 件名 + 本文
   threadKey  = 件名（同じ件名を 1 つのスレッドにまとめる）
   mention    = 宛先に自分が含まれるか
   meta       = { messageId, references, inReplyTo }
   ↓
コアフローへ

返信：

チケットが返信する
   ↓
メールに翻訳：
   宛先     = 元の送信者（または指定先）
   件名     = Re: 元の件名
   本文     = メッセージ内容
   引用ヘッダ = 元の messageId
   ↓
SMTP で送信

4. 安定性：5 層の強化

目標：すべてのソースを 4 星以上に。

4.1 L1 — プロセス監視

独立したウォッチドッグ
   ↓ 15 秒ごと
生存確認：プロセスは生きているか？ポートは通じるか？
   ↓
異常 → 自動再起動（指数バックオフ：5s → 10s → 20s → 40s、上限 5 分）
   ↓
5 回連続で失敗 → 再起動を停止し、警告

なぜバックオフが必要か：バックオフしないと、壊れた依存が無限に再起動され、かえってシステムを圧迫します。

4.2 L2 — ポート調停

起動前に対象ポートを確認
   ↓
使用中？
   ├─ 自分のゾンビプロセス → 強制クリーンアップ
   ├─ 別のプログラム → ポートを変更、または予備ポートを使用
   └─ 判別不能 → 競合を報告し、人の判断を待つ

4.3 L3 — デュアルチャネル

重要な設計：各ソースは少なくとも 2 本の独立した経路を持ちます。

ソース主チャネル予備チャネル
GitHubAPIローカル git キャッシュ
WeChatローカルクライアントのプロトコルウィンドウコントロールの読み取り
メールIMAPPOP3
企業微信コールバック能動的なポーリング

主チャネルが落ちたら、自動で予備チャネルへ切り替えます。

4.4 L4 — メッセージの重複排除

同じメッセージが複数の経路から届くことがあります。プラットフォームのメッセージ ID で重複を排除します：

メッセージを受信
   ↓
ID キャッシュを照会
   ├─ 処理済み → 破棄
   └─ 新規 → 処理し、ID を記録（7 日間保持）

4.5 L5 — サーキットブレーカー保護

あるソースが連続して失敗
   ↓ しきい値に到達（既定 5 回）
「縮退」としてマーク
   ↓
動作が変わる：
   · 能動的なポーリングを行わない
   · 記録するだけで処理しない
   · パネルにオレンジの警告を表示
   ↓
人手による介入、または定期的な生存確認の成功で復帰

なぜ必要か：壊れたソースが再試行を続けると、すべての接続を占有し、他のソースを圧迫します。

5. 各ソースの詳細

5.1 企業微信（最も安定）

なぜ最も安定しているか：企業向けの公式 API で、プロトコルが安定しており、ドキュメントも揃っています。

2 つの接続方法：

方法能力複雑さ
グループボット Webhook送信のみ、受信不可極めて低い
アプリメッセージ API送受信可能中

推奨：アプリメッセージ API（受信できなければアサインできません）。

設定項目：

企業 ID (corpid)
アプリ Secret
AgentId
受信コールバック URL（任意、未設定ならポーリング）

5.2 QQ メール（最も場面に合う）

なぜ適しているか：メールは本質的に非同期で、送信者が分かり、件名でスレッドにまとめられます。

技術的な要点：

項目値
受信imap.qq.com:993（SSL）
送信smtp.qq.com:465（SSL）
認証認証コード（ログインパスワードではありません）
プッシュIMAP IDLE（サーバー側からの能動通知）

IMAP IDLE が鍵です。ポーリング不要で、新着メールをサーバーが通知するため、実質ゼロコストです。

切断時の処理：

IDLE 接続が切断
   ↓
即座に再接続（1 秒）
   ↓
再接続に失敗 → バックオフして再試行（5s / 15s / 60s）
   ↓
再接続に成功 → UID カーソルで切断期間のメッセージを補完取得

5.3 飛書

CLI は既にあり、アプリの認証情報が不足しています。

設定：自社アプリを作成し、App ID と App Secret を取得します。

能力：イベントストリームのプッシュ + メッセージの送受信。

5.4 GitHub（4 段ミラー）

これは本プロジェクトの重要な設計です。GitHub は一部の地域でアクセスが不安定だからです。

第 1 段：api.github.com       直結
    ↓ 失敗
第 2 段：高速化ミラー          サードパーティのプロキシ
    ↓ 失敗
第 3 段：ローカル git キャッシュ  すでに clone 済みの内容
    ↓ 失敗
第 4 段：一括ダウンロード      zip を取得して展開

各段が失敗すると自動で縮退し、人手の介入は不要です。

設定項目：

☑ 本家サイト
☑ ミラー1（高速化プロキシ）
☑ ミラー2（ローカルキャッシュ）
☑ ミラー3（一括ダウンロード）

5.5 Gmail

技術的な要点：

項目値
受信imap.gmail.com:993（SSL）
認証アプリ専用パスワード（2 段階認証の有効化が必要）
ネットワークプロキシが必要（一部の地域）

注意：Gmail は一部の地域で直結するとタイムアウトするため、必ずプロキシを経由します。

5.6 QQ

ブリッジは既にあり、WebSocket を使います。

強化ポイント：

  • ハートビートによるキープアライブ（30 秒ごとに ping）
  • 切断時の自動再接続
  • 再接続後にオフラインメッセージを補完取得

5.7 WeChat（重点的な強化）

ここが最も脆弱な部分であり、5 層の強化が必要です。

なぜ脆弱なのか

問題説明
公式 API がないローカルクライアント経由しかありません
マルチプロセス構成4 つの子プロセスがあり、どれかが落ちると全滅します
ポートの取り合い2 つのコンポーネントが同じポートを奪い合います
クライアントの改版Tencent が更新するたびに追随が必要です

5 層の強化

層手段解決する問題
L1 プロセス監視15 秒ごとの生存確認、クラッシュ時に再起動プロセスの停止
L2 ポート調停起動前にゾンビプロセスを掃除ポートの取り合い
L3 デュアルチャネル主チャネルが落ちたら → ウィンドウコントロールの読み取り単一障害点
L4 メッセージ重複排除メッセージ ID で重複排除二重処理
L5 サーキットブレーカー連続失敗で縮退・警告全体の圧迫

L3 が鍵：ウィンドウコントロールの読み取り

原理：Windows の UIAutomation は、WeChat ウィンドウ内のコントロールツリー（メッセージ一覧、入力欄、送信ボタン）を直接読み取れます。

長所：

  • サードパーティの注入に依存しません
  • WeChat クライアントを改変しません
  • 独自プロトコルを使いません

短所：

  • WeChat の改版でコントロール構造が変わる可能性があり、適応が必要です
  • 読み取り速度はプロトコルより遅いです

なぜこれで 4 星に届くのか：独立した経路が 2 本あり、片方が落ちてももう片方が残るからです。

なぜ 5 星に届かないのか

本質的に Tencent クライアントの挙動に依存しているからです。 Tencent はいつでも改版でき、こちらは追随するしかありません。

4 星が誠実な上限であり、5 星と言うのは嘘になります。

6. ヘルス状態

各ソースはヘルス状態を報告します：

状態意味パネルの色
ready正常に動作中緑
starting起動中青
paused一時停止（設定が未完了）灰
errorエラー橙
degraded縮退（サーキットブレーカー中）赤

状態は項目ごとに分かれています：

runtime  : ready     ← ホスト層
github   : error     ← 業務層、こちらが重要
email    : ready

注意：runtime: ready はソースが正常であることを意味しません。必ず業務層の状態を見てください。

7. 新しいソースの追加

本プロジェクトが未対応のプラットフォームに接続する場合の手順：

  1. プロトコルを決める：API / IMAP / WebSocket / ローカルクライアント
  2. 必須の 3 項目を実装する：設定フォーム、トリガー翻訳、返信チャネル
  3. 登録する：ソースレジストリで宣言します
  4. テストする：設定 → 接続テスト → テストメッセージを 1 通送信

作業量：約 300〜600 行、2〜4 時間。
