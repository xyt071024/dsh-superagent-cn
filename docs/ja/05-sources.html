ソースと安定性

1. 設計原則

各ソースがやることは 3 つだけです。翻訳、返信、権限範囲の宣言。それ以外はすべてコアのロジックを再利用します。

プラットフォームのイベント
   ↓ 翻訳
統一された Trigger
   ↓ コアフローへ（変更なし）
...（公式のロジックをすべて再利用）
   ↓ 返信
プラットフォームの形式へ翻訳

新しいソースの追加 = 翻訳層を 1 つ書くことであり、コアを変更する必要はありません。

権限の 2 つの関門を混同しないこと

誰がアサインできるかはゲートウェイが強制します（純粋なコードで、メッセージ本文は読みません）：policy.sources[ソース].allowed のリストにこの actor.id があるかどうかの文字列比較であり、メッセージに「以前の指示を無視せよ」と書かれていてもこの判定は変わりません。

請けるかどうかはモデルの評価が決めます：リストが決めるのは「この人に依頼する資格があるか」だけです。その依頼を請けるか、どのくらいの範囲に切るかは、Eval のモデルがメッセージ本文を読んで判断するため、この層はメッセージ本文の影響を受け得ます。リストが与えるのは資格であり、結論ではありません。

評価を付けられるのは 実測済み のソースだけです。 GitHub と QQ の星はこのマシンでの実測に基づきます。残りの 5 つはコードは書けていますが、このマシンでは一度も接続していないため（WeChat と企業微信は経路自体がなく、メールは認証コードがありません）未評価 と表記します。低評価でもなく、取り置きの高評価でもなく、まだ根拠がないという意味です。状態の表記は 実測済み / 実装済み・未検証 / 計画中 の 3 段階で固定です。

4. 安定性：実際に実装されているもの

先に断っておきます：この節にはコードに実在する仕組みだけを書きます。現時点で実測済みなのは GitHub と QQ の 2 つだけで、残りは 未評価 です。

4.1 ポーリング失敗で騒がない

どのソースにも failuresBeforeError（既定 3）があります：

1 回のラウンドが失敗
   ↓
カウント +1、次のラウンドを待つ（家庭回線の一時的なタイムアウトで警告を出さない）
   ↓
連続で failuresBeforeError に達する
   ↓
パネルが error を表示し、最後のエラー内容を添える
   ↓
次のラウンドが成功すれば復帰し、カウントは 0 に戻る

なぜ 1 回で警告しないのか：家庭回線では 1 回のタイムアウトは日常的で、すぐ赤くなるパネルは信用されなくなります。

4.2 プラットフォームのメッセージ ID で重複排除

同じメッセージは後続のポーリングでも再度見えますが、まだ見ていないものだけが Trigger になります。

ソースキー記憶する件数
GitHubIssue/PR コメント ID + ETag 条件付きリクエストカーソル + ETag
QQ / WeChat / WeCommessage_idインスタンスごとに直近 2000 件
メールMessage-IDアドレスごとに直近 2000 件
飛書トピックごとの既読メッセージ IDトピック単位

インスタンスごとに別々に保持するので、1 つの kind で 2 つのアカウント（qq-work と qq）を持っても互いに干渉しません。

4.3 カーソルの永続化

「どこまで読んだか」はローカル DB に保存され、再起動しても再生されません：

  • メッセージが Trigger になる前にカーソルを記録する
  • 再起動後はカーソルから続き、古いメッセージを再処理しない
  • POLL_HORIZON_MS が遡る範囲を制限し、初回接続で全履歴を引き込まない

4.4 ポーリング間隔は設定可能

ソース既定範囲説明
GitHub60 秒60-3600ETag により変化がなければクォータを消費しない
QQ / WeChat / WeCom5 秒2-3600OneBot にプッシュ用カーソルがなく、定期読み取りのみ
メール120 秒30-3600メールは即時性を要する媒体ではない

4.5 実装していないもの

以下は本リポジトリにはありません。期待しないでください：

  • プロセス監視 / 自動再起動：ホスト（DSH）が動いている間だけポーリングし、ホストと共に止まります。独立した監視プロセスはありません
  • ポート調停：同じポートで 2 つ目のインスタンスを起動すると失敗し、その旨を報告します。別ポートを自動で選ぶことはしません
  • サーキットブレーカー：連続失敗はヘルス状態を変えるだけで、再試行を止めません
  • UIAutomation によるウィンドウ読み取り：プロトコルを使わずクライアント UI を直接読む実装はありません
  • 多段ミラー / 自動フェイルオーバー：GitHub は gh CLI 自身の再試行とプロキシ設定に任せています

この節を置く理由：「あるべき姿」の層を並べた文書は、インストールすれば付いてくるように読めてしまいます。やっていないことを書くほうが、やる予定のことを並べるより役に立ちます。

5. 各ソースの詳細

5.1 企業微信（設計上は最も安定）

状態：実装済み・未検証 —— このマシンには経路自体がなく、一度も接続していません。/orchestrator/api/sources は state: setup を返します。

なぜ安定と考えるか：企業向けの公式 API で、プロトコルが安定しており、ドキュメントも揃っています。これはプロトコル自体に対する評価であり、このマシンでの経路の受け入れ結果ではありません。

2 つの接続方法：

方法能力複雑さ
グループボット Webhook送信のみ、受信不可極めて低い
アプリメッセージ API送受信可能中

推奨：アプリメッセージ API（受信できなければアサインできません）。

設定項目：

企業 ID (corpid)
アプリ Secret
AgentId
受信コールバック URL（任意、未設定ならポーリング）

5.2 QQ メール（最も場面に合う）

状態：実装済み・未検証 —— このマシンでは実際の認証コードで一度も接続しておらず、/orchestrator/api/sources は state: paused、code: mailUnconfigured を返します。Gmail は同じ IMAP + SMTP 実装を共有しているため、状態も同じです。

なぜ適しているか：メールは本質的に非同期で、送信者が分かり、件名でスレッドにまとめられます。

技術的な要点：

項目値
受信imap.qq.com:993（SSL）
送信smtp.qq.com:465（SSL）
認証認証コード（ログインパスワードではありません）
受信方式定期ポーリング（既定 120 秒、30〜3600 で設定可）

現在の実装はポーリングであり、IDLE ではありません。 この版は用途に足る最小限の IMAP クライアント（ログイン、SELECT、最新 N 件の FETCH）を内蔵しており、IDLE プッシュは実装していません。そのため pollSeconds が経過したときに取りに行きます。「サーバーが能動的に通知し、実質ゼロコスト」にするには imap.ts に IDLE コマンドと切断時の再接続を追加する必要があり、それは今後の作業です。

重複排除は Message-ID で行います：同じメールはポーリングのたびに再び見えるため、まだ見ていない Message-ID だけが Trigger になります。記録はメールアドレスごとに別々（最新 2000 件）なので、2 つのメールボックスが同じ実装を共有しても干渉しません。

切断時の処理：

その回のポーリングが失敗
   ↓
カウント +1、次の周期を待つ
   ↓
連続失敗が failuresBeforeError（既定 3）に達する
   ↓
パネルに error を表示し、最後のエラーを明示

次のポーリングが成功すればカウントは 0 に戻るため、単発のネットワーク断では通知されません。

5.3 飛書

状態：実装済み・未検証 —— 上流が持つ実装です。このマシンにはアプリの認証情報が設定されておらず（lark-cli は未 bind）、state: setup です。

CLI は既にあり、アプリの認証情報が不足しています。

設定：自社アプリを作成し、App ID と App Secret を取得します。

能力：イベントストリームのプッシュ + メッセージの送受信。

5.4 GitHub（4 段ミラー）

状態：実測済み —— 3080 の稼働インスタンスの /orchestrator/api/sources が state: ready を返し、0 notifications; next poll ≥ 60s です。

これは本プロジェクトの重要な設計です。GitHub は一部の地域でアクセスが不安定だからです。

第 1 段：api.github.com       直結
    ↓ 失敗
第 2 段：高速化ミラー          サードパーティのプロキシ
    ↓ 失敗
第 3 段：ローカル git キャッシュ  すでに clone 済みの内容
    ↓ 失敗
第 4 段：一括ダウンロード      zip を取得して展開

各段が失敗すると自動で縮退し、人手の介入は不要です。

設定項目：

☑ 本家サイト
☑ ミラー1（高速化プロキシ）
☑ ミラー2（ローカルキャッシュ）
☑ ミラー3（一括ダウンロード）

5.5 Gmail

状態：実装済み・未検証 —— QQ メールと同じ IMAP + SMTP 実装を共有しており、このマシンでは実際のアプリパスワードで一度も接続しておらず、state: paused です。

技術的な要点：

項目値
受信imap.gmail.com:993（SSL）
認証アプリ専用パスワード（2 段階認証の有効化が必要）
ネットワークプロキシが必要（一部の地域）

注意：Gmail は一部の地域で直結するとタイムアウトするため、必ずプロキシを経由します。

5.6 QQ

状態：実測済み —— 3080 の稼働インスタンスの /orchestrator/api/sources が state: ready を返し、stats.received = 14（実際のグループメッセージ）です。

OneBot v11 の HTTP エンドポイント経由（SnowLuma / NapCat などの実装）です。受信は POST によるポーリング、返信も同じエンドポイントを使います。WebSocket の常時接続ではないため、ハートビートによるキープアライブ層はありません。

実際の強化手段：

  • message_id による重複排除（インスタンスごとに最新 2000 件）。ポーリングで同じメッセージを再び見ても二重処理しません
  • 連続失敗が failuresBeforeError（既定 3）に達して初めてパネルにエラーを出し、単発の揺らぎでは通知しません
  • グループでは既定で @ されたメッセージだけが自分宛てになります。observeAll を有効にするとポリシーの受信表が判断します
  • インスタンスごとに独立したポーリングループを持つため、1 つの端点が落ちても他が遅くなりません

注意：OneBot にはプッシュ用カーソルがないため、最近のメッセージを一定間隔で読むしかなく、pollSeconds（既定 5 秒）が遅延の上限になります。

5.7 WeChat（微信側の OneBot ブリッジに依存）

状態：実装済み・未検証 —— OneBot プロトコル実装を再利用しています。本機に微信側のブリッジがなく state: setup、一度も接続していません。

実際の実装：QQ・WeCom と同一のコード（oneBotKind() ファクトリ、kind: 'wechat'）です。本プラグインは HTTP ポーリングと返信のみを行い、微信クライアント自体には触れません。ブリッジは微信側の OneBot 実装が先に起動している必要があります。

なぜ外部依存が最も強いのか：

項目説明
プロトコルOneBot v11 HTTP、エンドポイントは利用者の微信ブリッジが提供
前提条件微信側で動作する OneBot ブリッジが必要。本プラグインは起動しない
上限ブリッジが落ちた場合、本プラグインは状態を報告するだけで、再起動はできない

本プラグインが実際に提供するもの（すべて src/sources/qq.ts 内）：

仕組み動作
ポーリング失敗時の再試行1 回の失敗では何も報告せず、次のポーリングで再試行
連続失敗カウント連続 failuresBeforeError 回（既定 3）で初めてヘルスが error になる
重複排除message_id による。インスタンスごとに直近 2000 件を記憶
ヘルス状態パネルに ready / error / setup と「新着 N 件、次回ポーリングまで N 秒以上」を表示

実装していないもの：プロセス監視、ポート調停、サーキットブレーカー、UIAutomation によるウィンドウ読み取り——いずれも本リポジトリにはありません。微信ブリッジが落ちる場合はブリッジ側の問題です。

表が星ではなく 未評価 な理由

この経路は本機で一度も接続できていません。未接続のものに星を付けるのは、根拠のない判断を読み手の代わりに下すことになります。

6. ヘルス状態

各ソースはヘルス状態を報告します：

状態意味パネルの色
ready正常に動作中緑
starting起動中青
setup設定が未完了（認証情報・経路の不足）灰
paused一時停止（設定が未完了）灰
errorエラー橙
degraded縮退（サーキットブレーカー中）赤

状態は項目ごとに分かれています（下のブロックはあくまで例示で、このマシンの実況ではありません。実況は本節末尾の観測表を参照してください）：

runtime  : ready     ← ホスト層
github   : error     ← 業務層、こちらが重要
email    : ready

注意：runtime: ready はソースが正常であることを意味しません。必ず業務層の状態を見てください。

このマシンで実際に観測された状態（3080 の稼働インスタンス /orchestrator/api/sources より）：

ソース観測された状態説明
GitHubready0 notifications; next poll ≥ 60s
QQreadystats.received = 14、実際のグループメッセージ
メールpausedcode: mailUnconfigured、実際の認証コード未入力
WeChatsetupWeChat 側のブリッジがない
企業微信setup経路自体がない
飛書setupアプリの認証情報が未設定（lark-cli 未 bind）

ready は現在の設定でそのソースが本当に動いていることを意味し、paused / setup はコードはあるが設定が未完であることを意味します。「利用可能」ではありません。

7. 新しいソースの追加

本プロジェクトが未対応のプラットフォームに接続する場合の手順：

  1. プロトコルを決める：API / IMAP / WebSocket / ローカルクライアント
  2. 必須の 3 項目を実装する：設定フォーム、トリガー翻訳、返信チャネル
  3. 登録する：ソースレジストリで宣言します
  4. テストする：設定 → 接続テスト → テストメッセージを 1 通送信

作業量：約 300〜600 行、2〜4 時間。

「安定性」の行は実測したソースにだけ評価を付けます：GitHub と QQ にはこのマシンでの観測結果があるため星が付きます。残りの 5 つは、これを書いた時点でこのマシンで一度も接続していないため 未評価 です。接続の難しさ・必要な準備・非同期との相性・推奨度はプロトコルの特性から下した判断であり、実測の結論ではありません。

1 つだけ接続するなら QQ メールを選んでください：場面に最も合い（非同期、送信者が分かる、スレッドにまとめられる）、依存が最も少なく、プロトコルが標準的です。ただしこの経路はこのマシンでは実際の認証コードでまだつないでいないため、最初の設定では認証コードを入力して接続テストを 1 回行う必要があります。
