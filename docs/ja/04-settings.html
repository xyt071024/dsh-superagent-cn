3 つのポリシーの比較

ポリシー長所短所適する場面
統一モデル安価で予測しやすい難問では効果が落ちますタスクが同質な場合
段階別モデル必要な分だけ課金段階の設定が必要ほとんどの場面
マルチモデル並行効果が最大最も高価重要なタスク

思考深度の効果

思考深度は token 消費と推論品質に直接影響します：

段階相対コスト用途
極低1x難易度の事前判定、分類
低2x単純な書き換え、整形
中4x通常のコーディング
高8x複雑なロジック、アーキテクチャ設計
最高16x極めて難しい推論、自己進化

難易度の事前判定に「極低」を使うのがコスト管理の要です。50 token の判断で、数百 token の無駄を避けられます。

統一連絡先センターについて

公式の設計はあえてソースをまたぐ身元マッピングを行っていません。本プロジェクトはこの層を追加しています。「同じ人物ならどこでも許可リスト扱い」というのは必須要件だからです。

{
  "uid": "owner",
  "identities": {
    "github": ["<アカウント>"],
    "email": ["<アドレス>"],
    "qq": ["<番号>"],
    "wecom": ["<アカウント>"],
    "feishu": ["<open_id>"]
  },
  "policy": {
    "canRequest": true,
    "canProactive": false
  }
}

自主権限を項目ごとに分ける理由

「自主性を許すか」は 1 つの〇×問題ではなく、十数個の〇×問題です。

権限リスク
推定リクエストの自主受注望まないことをする可能性があります
プラグインの自主導入信頼できないコードを入れる可能性があります
自分のコードの自主変更壊す可能性があります
メッセージの自主送信言い間違える可能性があります
ファイルの自主削除取り返しがつきません

推奨：まずすべてオフにし、1 週間観察してから 1 項目ずつオンにしてください。

「プロセス環境変数の分離」が重要な理由

このプラグインはプロセスの PATH を書き換え、gh と lark-cli のラッパースクリプトを先頭に挿入します。

統合版では、同プロセスの他のプラグインにも影響します。分離スイッチをオンにすると、内部でのみ独自の環境を使い、グローバルを汚しません。

統合版ではこの項目を必ずオンにしてください。
