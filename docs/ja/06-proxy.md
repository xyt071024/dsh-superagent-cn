## 1. なぜプロキシが必要なのか

一部のサービスは、特定の地域からのアクセスが不安定です：

| サービス | 問題 |
|---|---|
| GitHub API | 断続的なタイムアウト |
| raw.githubusercontent.com | 頻繁にリセットされる |
| Gmail IMAP | 直結でタイムアウトする |
| 一部の npm / pypi ソース | 遅い |

**すべてのソースにプロキシが必要なわけではありません。** 中国国内の企業微信、飛書、QQ、QQ メールは**直結が最速**で、プロキシを経由するとかえって遅くなります。

---

## 2. 三層アーキテクチャ

```
┌─────────────────────────────────────────────┐
│  L1：ユーザープロキシ（最優先）             │
│  · ユーザー自身が設定したもの               │
│  · 手動入力 / ドラッグ認識に対応            │
└─────────────────────────────────────────────┘
                  ↓ なければ
┌─────────────────────────────────────────────┐
│  L2：システムプロキシ                       │
│  · システム設定のプロキシを読む             │
│  · Windows: レジストリ Internet Settings    │
└─────────────────────────────────────────────┘
                  ↓ なければ
┌─────────────────────────────────────────────┐
│  L3：内蔵プロキシ                           │
│  · ユーザーが提供したサブスクリプション     │
│  · またはローカルの既存プロキシを再利用     │
└─────────────────────────────────────────────┘
                  ↓ どれもなければ
┌─────────────────────────────────────────────┐
│  L4：直結                                   │
└─────────────────────────────────────────────┘
```

**優先順位**：ユーザープロキシ > システムプロキシ > 内蔵プロキシ > 直結

## 3. ユーザープロキシ：2 つの設定方法

### 3.1 手動入力

```
HTTP   [ http://127.0.0.1:____ ]
SOCKS5 [ socks5://127.0.0.1:____ ]
```

プロキシのポートを把握しているユーザー向けです。

### 3.2 ドラッグ＆ドロップ認識（かんたん設定）

```
┌────────────────────────────────────────────┐
│                                            │
│  プロキシソフトの実行ファイルかフォルダを  │
│  ここにドラッグ                            │
│                                            │
│      [ ドラッグ領域 / クリックで選択 ]     │
│                                            │
└────────────────────────────────────────────┘
```

**認識フロー**：

```
ユーザーがファイル/フォルダをドラッグ
   ↓
1. ディレクトリ構造をスキャンし、ソフトの種類を判定
   · 実行ファイル名を見る（既知ソフトの特徴）
   · 設定ファイルを見る（config.json / clash.yaml など）
   · プロセス名を見る
   ↓
2. 設定からプロキシポートを見つける
   · 設定ファイルから読む
   · または一般的な既定ポートを探査（7890 / 1080 / 7891 など）
   ↓
3. 実際にそのポートが使えるか試す
   · 接続を試す
   · それ経由でテスト用アドレスにアクセスしてみる
   ↓
4. 成功 → 設定を保存
   失敗 → 「X を認識しましたが、ポートが通りません。手動で入力してください」と表示
```

**自動認識に対応する種類**（例。実際は特徴マッチングで判定）：

| 種類 | 特徴 |
|---|---|
| 設定駆動型 | `config.yaml` / `config.json` があり、ポート項目を含む |
| GUI クライアント型 | GUI があり、ポートは設定画面に書かれている |
| コマンドライン型 | カーネルの実行ファイルがあり、引数にポートが含まれる |

### 3.3 自動起動と引継ぎ

```
プロキシが未起動であることを検知
   ↓
☑ 認識済みのプロキシを自動起動
   ↓
プログラムを起動（GUI の立ち上がりを待つ場合がある）
   ↓
⚠ 対話が必要な場合（ログイン / 広告視聴 / 確認クリック）
   ↓
☑ 対話を自動で完了
   ↓
内蔵ブラウザで開き、必要なボタンを自動クリック
   ↓
接続確立を待つ（ポート探査 + テストリクエスト）
   ↓
成功したら処理を開始
```

**「広告視聴の自動化」について**：

一部の無料プロキシは、起動時に広告を見ないと接続できないものがあります。自動化の手順は次のとおりです：

1. その画面を開く（Web 版なら内蔵ブラウザを使う）
2. 広告のカウントダウン終了を待つ
3. 「スキップ」または「閉じる」を自動クリック
4. 接続済みであることを確認

**これはソフトごとの個別対応が必要**で、汎用的な機能ではありません。画面上に「対応済みのソフトのみサポート」と明記する必要があります。

## 4. システムプロキシ

```
システムプロキシ設定を読み取る
   ↓
Windows: HKEY_CURRENT_USER\...\Internet Settings
   · ProxyEnable
   · ProxyServer
   ↓
有効なら → 使用する
無効なら → スキップ
```

**検出は既定で有効**です。多くのユーザーはプロキシソフトを起動するとシステムプロキシが自動設定されるためです。

## 5. 内蔵プロキシ

### 5.1 3 つのノードソース

| ソース | 説明 | 推奨度 |
|---|---|---|
| **ユーザー提供のサブスクリプション** | サブスクリプションリンクを入力すると、ノードを自動取得 | ★★★★★ |
| **ローカルの既存を再利用** | 認識済みのプロキシプログラムを使う | ★★★★★ |
| **内蔵の無料ノードプール** | 公共ノードをまとめて内蔵 | ⚠ 下記参照 |

### 5.2 無料ノードについて —— はっきり書いておくべきこと

**公共の無料ノードは、その大半がクリーンではありません。**

| リスク | 説明 |
|---|---|
| **IP が大量に共有される** | 1 つの IP を何万人もが使うことがあり、主要サービスからは拒否されたりアカウント停止されたりします |
| **認証情報が傍受されうる** | プロキシ事業者はあなたのすべてのトラフィック（token や認可コードを含む）を見られます |
| **いつ切れてもおかしくない** | 無料ノードの寿命は、通常は時間単位です |
| **速度が不安定** | 直結より遅くなることもあります |

**本プロジェクトのスタンス**：

- この選択肢は用意するが、**既定ではオフ**
- 画面上にリスクを明示する
- **出所不明のノードは内蔵しない**
- ユーザー自身のサブスクリプションを使うか、既存のプロキシを再利用することを推奨する

**どうしても無料ノードを使う場合の推奨**：
- 公開コンテンツへのアクセスのみに使う（認証情報は送らない）
- 重要な操作（GitHub へのプッシュ、メール受信）はユーザー自身のプロキシを通す

### 5.3 ノードのヘルスチェック

```
ノードプールに追加
   ↓
定期テスト（30 分ごと）
   · 接続できるか
   · レイテンシはどれくらいか
   · 対象サービスにアクセスできるか
   ↓
スコアリング
   ↓
スケジューリング時は高スコアのノードを優先
   ↓
3 回連続で失敗 → 一時的にプールから外す
```

## 6. ドメイン別ポリシー

**すべてのトラフィックがプロキシを通るべきではありません。**

```
┌─────────────────────────────────────────────┐
│  ドメイン                   経由？  ノード  │
├─────────────────────────────────────────────┤
│  api.github.com             ☑       自動    │
│  raw.githubusercontent      ☑       自動    │
│  github.com                 ☑       自動    │
│  imap.gmail.com             ☑       自動    │
│  smtp.gmail.com             ☑       自動    │
│  imap.qq.com                ☐       直結    │
│  smtp.qq.com                ☐       直結    │
│  企業微信 API               ☐       直結    │
│  飛書 API                   ☐       直結    │
│  qq.com                     ☐       直結    │
│  bilibili.com               ☐       直結    │
├─────────────────────────────────────────────┤
│  ☑ 記載のないドメインは既定で直結           │
└─────────────────────────────────────────────┘
```

**なぜ中国国内のサービスは直結するのか**：プロキシを通すと遠回りになり、レイテンシが高くなり、プロキシのトラフィックも無駄に消費します。

## 7. 失敗時の処理

### 7.1 段階的リトライ

```
リクエスト失敗
   ↓
1 回目のリトライ：即時（ノードを変更）
   ↓ 失敗
2 回目のリトライ：1 秒後（ノードを変更）
   ↓ 失敗
3 回目のリトライ：3 秒後（ノードを変更）
   ↓ 失敗
縮退：直結を試す
   ↓ 失敗
失敗を報告（試行記録を添えて）
```

### 7.2 サーキットブレーカー

```
あるプロキシが 5 回連続で失敗
   ↓
使用不可としてマーク（10 分間のクールダウン）
   ↓
その間のすべてのリクエストは他のプロキシまたは直結を通す
   ↓
10 分後に再テスト
```

### 7.3 フェイルファスト

**壊れたプロキシの上で長く待ってはいけません。**

```
接続タイムアウト：5 秒
読み取りタイムアウト：30 秒
総タイムアウト：60 秒
```

## 8. 実装インターフェース

```
proxy.resolve({
  target: 'api.github.com',
  prefer: 'user' | 'system' | 'builtin' | 'direct' | 'auto'
})
→ {
    agent,              // 実際の接続設定
    protocol: 'http' | 'socks5' | 'direct',
    source: 'user' | 'system' | 'builtin' | 'direct',
    node: 'ノード識別子（内蔵の場合）'
  }
```

**呼び出し側は「接続できるか」だけを気にすればよく、「どう接続するか」を気にする必要はありません。**

[設定画面 · グループ 5：プロキシ](04-settings.md#グループ-5プロキシ) を参照してください。

主要な要素：

| ドメイン別テーブル | ドメインごとに個別設定 |

## 10. よくある質問

### Q：プロキシソフトはすでに起動しています。ここでも設定が必要ですか？

**通常は不要です。** プロキシソフトがシステムプロキシを設定していれば、本プロジェクトが自動で検出して使用します。

システムプロキシを設定していない場合（TUN モードのみ）でも、直結で通るので設定は不要です。

**手動設定が必要なケース**：プロキシソフトがシステムプロキシも TUN も設定せず、ローカルポートだけをリッスンしている場合です。

### Q：プロキシを設定すると他のプログラムに影響しますか？

**影響しません。** 本プロジェクトのプロキシ設定は自身のリクエストにのみ作用し、システム設定は変更しません。

### Q：無料ノードは使えますか？

**認証情報が絡む操作には使わないでください。** たまに公開ドキュメントを眺める程度なら検討の余地はありますが、GitHub へのプッシュやメール受信のような操作は必ず信頼できる経路を通してください。

### Q：なぜ中国国内のサービスを直結に設定するのですか？

プロキシを通すと、トラフィックが海外を経由して戻ってくるため、レイテンシが大幅に増えます。中国国内の企業微信、飛書、QQ は直結が最速です。
