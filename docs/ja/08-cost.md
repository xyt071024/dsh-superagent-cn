## 1. なぜコスト管理が必要なのか

マルチセッション協調では、**1 つのタスクで 6 つのセッションを開く**ことがあります。そのすべてで最強モデル・最高思考深度を使うと、コストは単一セッションの十数倍になります。

**コストが制御不能になる典型例**：

```
「中程度」のタスク
   ↓ 難易度の事前判定をしなかった
サブセッションを 6 個開いた
   ↓ すべて最強モデル
   ↓ すべて最高思考深度
   ↓ 各セッションが同じコンテキストを重複して読む
総消費 = 単一セッションの 20 倍以上
```

**コスト管理の目的は「出費を減らすこと」ではなく、「無駄な出費をしないこと」です。**

## 2. 3 段階の制御

### L1：タスク難易度の事前判定（最も効果的）

```
タスクが到着
   ↓
非常に軽量なモデルで 1 回だけ分類を実行
   · モデル：最も安いもの
   · 思考深度：極低
   · 出力：1 語
   ↓
約 50 token
   ↓
以降の方針を決定
```

**50 token で数百から数千 token の節約になる。これがコストパフォーマンス最良の一手です。**

### L2：難易度別の段階分け

| 難易度 | モデル階層 | 思考深度 | サブセッション数 |
|---|---|---|---|
| **simple** | 安価なモデル | 低 | 0（自分で実行） |
| **medium** | 標準モデル | 中 | 0-2 |
| **complex** | 強力なモデル | 高 | 3-4 |
| **extreme** | 強力なモデル | 最高 | 5-6 |

### L3：実行中の縮退

```
実際の消費を監視
   ↓
予算の 80% を超過
   ↓
⚠ 警告 + 以降のタスクを段階を下げる
   ↓
100% を超過
   ↓
一時停止（あなたの決定待ち）
```

## 3. 難易度事前判定の実装

### 3.1 プロンプト

```
このタスクの複雑度を判定し、1 語だけ出力してください：

simple  —— 単一ファイルの小さな変更、簡単な質疑応答、書式調整
medium  —— 複数ファイルの調整、コンテキストの理解が必要
complex —— モジュール横断のリファクタリング、設計案が必要
extreme —— アーキテクチャ判断が必要、複数システムの統合

タスク：
{task}
```

### 3.2 なぜ「極低」思考深度を使うのか

分類タスクに深い推論は不要です。「極低」を使う理由：
- コストは「最高」の約 1/16
- 精度の低下はわずか（タスク記述は通常十分に明確なため）

### 3.3 誤判定への対処

**事前判定は外れることがあります。** 2 つのケースがあります：

| ケース | 対処 |
|---|---|
| 「簡単」と判定したが実際は難しい | 実行中に詰まりを検知 → 昇格して再判定 |
| 「複雑」と判定したが実際は簡単 | 最初の 2 分で進展がなければ → 降格して自分で実行 |

**判断の根拠**：実行から 2 分後に進捗を確認し、「簡単」タスクがまったく進んでいなければ再評価します。

## 4. コンテキストの再利用

### 4.1 問題

同じスレッドのメッセージを、複数のチケットが読む必要があります。毎回読み直す = 重複消費です。

### 4.2 解決策

```
あるスレッドを初めて読む
   ↓
要約 + 重要断片をキャッシュ
   ↓
以降のチケットは読む → キャッシュにヒット
   ↓
追加された部分だけ補う
```

**キャッシュの有効期間**：スレッドに新着メッセージがあれば、該当部分を無効化します。

### 4.3 キャッシュの粒度

| 内容 | キャッシュ方針 |
|---|---|
| スレッドの全履歴 | 要約キャッシュ（重要事実を保持） |
| リポジトリのファイル | commit hash 単位でキャッシュ |
| モデルの応答 | KV Cache（同一プレフィックスを再利用） |

## 5. 結果のキャッシュ

### 5.1 キャッシュできるもの

| キャッシュ可 | キャッシュ不可 |
|---|---|
| コード分析の結果 | リアルタイム状態に関わるもの |
| ドキュメントの要約 | 現在時刻に依存するもの |
| ファイル構造 | 最新データが必要なもの |
| 類似タスクの解法 | ユーザーが明示的にやり直しを求めたもの |

### 5.2 キャッシュキー

```
key = hash(タスク種別 + 対象ファイル + 対象ファイルの hash + 主要パラメータ)
```

**ファイルが変われば、キャッシュは無効になります。**

## 6. モデル段階分けの方針

### 6.1 3 つの方針の比較

| 方針 | コスト | 効果 | 適用場面 |
|---|---|---|---|
| **統一モデル** | 中 | 安定 | タスクが同質な場合 |
| **段階分けモデル** | 最も安い | 必要に応じて | ほとんどの場面 |
| **複数モデル並列** | 最も高い | 最良 | 重要なタスク |

### 6.2 段階分け設定の例

```
難易度事前判定 → 最も安いモデル   極低思考
簡単なタスク   → flash 級         低思考
中程度のタスク → 標準級           中思考
複雑なタスク   → 強力なモデル     高思考
極めて複雑     → 最強モデル       最高思考
自己進化       → 最強モデル       最高思考（頻度が低いので妥当）
```

### 6.3 思考深度とコストの関係

| 階層 | 相対 token 消費 |
|---|---|
| 極低 | 1x |
| 低 | 2x |
| 中 | 4x |
| 高 | 8x |
| 最高 | 16x |

**だからこそ「難易度事前判定は極低で」がこれほど重要なのです。**

## 7. 予算管理

### 7.1 3 層の予算

| 層 | 超過後 |
|---|---|
| **日次予算** | 一時停止（段階を下げる設定も可） |
| **月次予算** | 一時停止 + 通知 |
| **単一タスク予算** | 段階を下げる、または中止 |

### 7.2 予算の表示

パネルにリアルタイム表示：

```
日次予算  ¥50
使用済み  ¥12.4  ▓▓▓▓▓░░░░░░░░░░░░░░░  24.8%
本日のタスク 8 件、平均 ¥1.55/タスク
```

### 7.3 予算超過時の処理

```
予算に接近（80%）
   ↓
⚠ 警告：以降のタスクは自動的に段階を下げる

予算超過（100%）
   ↓
⦿ 一時停止（既定）：新規タスクはキューに入り、あなたの決定待ち
○ 段階を下げる：継続するが安価なモデルのみ使用
○ 制限なし：通常どおり実行を継続
```

## 8. マルチセッションによるコストの増幅

### 8.1 コストモデル

```
単一セッションのコスト = C

N 個のセッションを並列実行：
  理論コスト = N × C
  実際コスト = N × C × 1.3（調整のオーバーヘッド）

ただし節約できる時間 = N 倍
```

**つまりマルチセッションは「お金で時間を買う」ということです。**

### 8.2 いつ価値があるか

| 価値がある | 価値がない |
|---|---|
| タスクが本当に並列化できる | 強い順序依存がある |
| 時間に敏感 | 急いでいない |
| 複雑度が高い | 簡単なタスク |
| コストが許容範囲 | 予算が厳しい |

### 8.3 コスト上限の保護

```
☑ 単一タスクのコスト上限  ¥ [ 10 ]
超過後：一時停止して確認
```

**1 つのタスクが誤って 1 日分の予算を焼き尽くすのを防ぎます。**

## 9. 実測データの参考値

以下は**サンプルデータ**です。実際はタスクとモデルによって異なります：

| シナリオ | 単一セッション | マルチセッション（4 個） | 倍率 |
|---|---|---|---|
| 簡単な文言修正 | ¥0.05 | 分割せず | 1x |
| 中程度の機能変更 | ¥0.8 | ¥2.4（3 個） | 3x |
| 複雑なリファクタリング | ¥5 | ¥18（5 個） | 3.6x |
| 極めて複雑なシステム | ¥20 | ¥60（6 個） | 3x |

**注意**：マルチセッションは N 倍のコストにはなりません。セッションごとのタスク範囲がより小さく、単一セッションあたりのコストが下がるためです。

## 10. コスト管理チェックリスト

リリース前の確認用：

| # | 項目 | 既定 | 説明 |
|---|---|---|---|
| 1 | ☑ タスク難易度の事前判定 | オン | 最も効果的なコスト管理手段 |
| 2 | ☑ 事前判定は極低思考 | オン | 16x のコスト差 |
| 3 | ☑ 結果キャッシュ | オン | 同一タスクを繰り返さない |
| 4 | ☑ コンテキスト再利用 | オン | 同一スレッドを読み直さない |
| 5 | ☑ 日次予算上限 | 必須 | 事故防止 |
| 6 | ☑ 単一タスク上限 | 入力推奨 | 単一タスクの暴走防止 |
| 7 | ☑ 予算超過時の自動段階下げ | オン推奨 | なだらかな処理 |
| 8 | ☐ 複数モデル並列 | 必要時 | 重要なタスクのみ |
| 9 | ☑ 自己進化の頻度低減 | 毎週 | 毎タスクの振り返りは不要 |

## 11. アンチパターン

| アンチパターン | 問題 |
|---|---|
| すべて最強モデルを使う | コスト 10 倍で、効果の向上は限定的 |
| すべて最高思考を使う | 同上 |
| すべてのタスクをマルチセッションに分割 | 調整オーバーヘッド > 利益 |
| 難易度事前判定をしない | 小さなタスクでも重い工程を通る |
| 予算上限を設定しない | 一度の事故で焼き尽くす |
| 毎タスクで深い振り返りをする | 振り返りコスト > タスクコスト |
